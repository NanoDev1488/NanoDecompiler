# HANDOFF_14: Косметическая чистка temp-переменных после HANDOFF_13
# (рекурсивного фикса пересечения стека)

Пользователь прямо попросил: "нету красивого кода - нельзя назвать
версию" - прежде чем публиковать под v1.4, нужно навести красоту в
выводе после HANDOFF_13 (тот фикс дал КОРРЕКТНЫЙ, но многословный код -
по несколько `__stkN` на каждый уровень цепочки пересечения стека).

## Три новых прохода (structure.py, внутри `simplify_stmts`)

Всё затрагивает ТОЛЬКО синтетические `__stkN`-переменные (проверка по
регулярке `^__stk\d+$`) - настоящие именованные локальные переменные
никогда не трогаются.

1. **`_collapse_temp_chains`** - `__stk4 = A; ...; __stk2 = __stk4;`
   (единственное дальнейшее использование `__stk4` в этом же списке -
   простое копирование) -> `__stk2 = A;`, `__stk4` убирается целиком.
   Работает до неподвижной точки (цепочки длиннее двух звеньев
   схлопываются за несколько внутренних итераций).

2. **`_hoist_common_branch_tail`** - если ПОСЛЕДНИЕ statements
   `then_body` и `else_body` - идентичные простые копирования `t = u;`
   (одно и то же в обеих ветках - типично для значения, которое просто
   "проезжает" через if не меняясь), выносим их из ОБЕИХ веток наружу,
   после if.

3. **`_inline_single_use_temps_anywhere`** - обобщение уже
   существовавшего `_inline_single_use_crossing_temps` (engine.py,
   который работал ТОЛЬКО для `t=X; return t;`). Новая версия
   подставляет `X` в место ЛЮБОГО следующего использования (вызов
   метода, `return`, `throw`) - не только `return`.

Все три плюс уже существовавшая `_fold_boolean_materialization`
(тернарная свёртка) гоняются в цикле (4 итерации, без раннего выхода -
сравнение AST-узлов через `==` ненадёжно, т.к. некоторые проходы мутируют
узлы на месте, что маскирует изменения при identity-based сравнении;
лишние проходы после схождения дёшевы и безопасны) - потому что каждый
проход может открыть возможность для другого: схлопывание цепочки может
привести if/else к виду, который тернарная свёртка узнаёт только СЕЙЧАС,
а результат свёртки - стать кандидатом на инлайн в место вызова.

## Результат - конкретные примеры (EryBuyer-v1.jar)

До:
```java
Player __stk1;
Object __stk2;
int __stk3;
Player __stk4;
Object __stk5;
int __stk6;
Player __stk7;
Object __stk8;
__stk1 = player;
__stk2 = this;
if (isAutobuyerEnabled(player)) {
    __stk6 = 0;
    __stk7 = __stk1;
    __stk8 = __stk2;
    __stk3 = __stk6;
    __stk4 = __stk7;
    __stk5 = __stk8;
} else {
    __stk3 = 1;
    __stk4 = __stk1;
    __stk5 = __stk2;
}
__stk5.setAutobuyer(__stk4, __stk3);
```

После:
```java
setAutobuyer(player, !isAutobuyerEnabled(player));
```

Другой пример (`PlaceholderAPIHook.apply`, 5 значений разом):

До: 5 объявлений `__stkN`, 5 присваиваний, потом
`return apply(__stk9, __stk8, __stk7, __stk6, __stk5);`

После:
```java
return apply(input, player, entry, amount, entry == null ? 0.0 : entry.priceX1);
```
