# HANDOFF_27: Модуль 4 - ir.py -> C++, сверено на всех джарах (4075/4075)

## ir.py -> ir.hpp/cpp

Перенесено полностью: `Instruction` (все поля - `pc/next_pc/opcode/
mnemonic/kind/ival/cp_index/target/targets/iinc_idx/iinc_const/atype/
count/dims`), пять computed-свойств (`is_branch/is_switch/is_return/
is_unconditional/is_conditional` - методы вместо `@property`, семантика
та же), `decode_method`.

Отдельно отмечу важную деталь, которую легко упустить при переносе: для
`wide iinc` и `wide <load/store>` Python **меняет** `ins.kind` на
`"iinc"`/`"local_ubyte"` (а не оставляет `"wide"`, как это делает
`disassembler.py` для отображения!) - то есть с точки зрения следующих
модулей (CFG/стек-машина) `wide iload 300` выглядит РОВНО как обычный
`iload`, просто с более широким индексом. Это разное поведение двух
модулей на одном и том же опкоде `0xC4` - в порте сохранено точно так же
(`ins.kind = OperandKind::IInc` / `OperandKind::LocalUByte`, никогда
`OperandKind::Wide`).

Также: fallback для `atype` на неизвестном коде типа - `"int"` (не
`f"type{t}"`, как в `disassembler.py` для текстового вывода) - в
`ir.py` это два РАЗНЫХ дефолта на один и тот же случай, оба сохранены
раздельно в соответствующих модулях порта.

### Найденное и исправленное расхождение (в инструменте сверки, не в порте)

Первый прогон дал 3607/4075 "расхождений" - при разборе оказалось, что
дело **только** в форматировании булевых полей: C++ `std::ostream <<

данные (какие именно инструкции branch/return/... и т.д.) совпадали
везде уже с первого прогона. Поправил `dump_ir.cpp` (не сам порт) на
явное `pybool()`, пересобрал, пересверил.

### Найденный и исправленный баг ПОРТА (важно, задним числом при работе над модулем 5)

При переносе `ins.targets` (карта switch: значение -> абсолютный pc, плюс
`None` -> default) изначально использовал `std::map<optional<int64_t>,
int64_t>` - показалось "то же самое, что Python dict". На самом деле НЕТ:
`std::map` сортирует по ключу, а `std::optional::nullopt` в C++ по
умолчанию сравнивается как "меньше любого значения" - то есть default
оказывался бы ПЕРВЫМ элементом при переборе, тогда как в Python-оригинале
`targets[None] = ...` выполняется ПОСЛЕДНИМ (после всех обычных значений)
и обычный `dict` (3.7+) сохраняет порядок ВСТАВКИ. Тест ЭТОГО модуля (4)
такое расхождение не поймал, потому что `dump_ir.cpp` сам нормализовал
(сортировал) targets для сравнения - ошибка обнаружилась только на модуле
5 (`cfg.py`), который использует `targets.items()` НАПРЯМУЮ, в порядке
словаря, для построения списка `succs` блока (порядок succs - часть
наблюдаемого поведения, используется дальше в `reverse_postorder`/
доминаторах). Исправлено: `SwitchTargets` теперь `std::vector<std::pair<
std::optional<int64_t>, int64_t>>`, вставка строго в том же порядке, что
Python (значения по возрастанию/по мере чтения bytecode, `default`
последним). Урок: тип "похожий на map по смыслу" - не повод считать
порядок несущественным, если исходный Python-объект - это `dict` (у
которого порядок ВСЕГДА гарантирован с 3.7) - нужно явно проверять, как
дальше используется этот порядок вызывающим кодом, а не полагаться на
"это же просто соответствие ключ->значение".
