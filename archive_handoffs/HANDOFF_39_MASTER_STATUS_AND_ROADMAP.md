### Найденный и исправленный КРИТИЧНЫЙ баг (сегфолт) - см. подробности в истории

`get_producer_temps`/`ensure_depth` (межблочная стыковка стека) в редких
случаях легитимно попадают в ситуацию, когда после `ensure_depth` размер
`exit_stack` НЕ совпадает с `needed` (это ПРОИСХОДИТ и в оригинале
тоже! Python в этом случае просто ловит `IndexError` через общий
`except Exception` и делает `ABORT: внутренняя ошибка декомпилятора:
IndexError...`). Мой C++ индексировал `cur_stack[...]` через
НЕПРОВЕРЯЕМЫЙ `operator[]`, что приводило к UB/сегфолту вместо
киданного исключения. **ИСПРАВЛЕНО**: заменил на `cur_stack.at(...)` -
теперь бросает `std::out_of_range`, ловится тем же `catch (const
std::exception&)`, даёт аналогичный (хоть и с другим текстом) ABORT -
поведение теперь БЕЗОПАСНОЕ (не крашится), хоть текст причины не 100%
совпадает с Python (`IndexError: list index out of range` vs
`vector::_M_range_check: ...`) - это ПРИЕМЛЕМО, не является критичным
расхождением (оба - "внутренняя ошибка декомпилятора", оба честно
откатываются на байткод).

### 5. Качество декомпиляции vs эталонные декомпиляторы (Vineflower)

Пользователь прислал сравнение: наш движок на одном реальном примере
(`MessageFormatter.java` из плагина `akytraps`) сгенерировал более
"сырой", близкий-к-байткоду код (Iterator вместо enhanced-for, лишние
касты типа `((Entry) x)`, явный `static { FIELD = ...; }` блок вместо
инлайн-инициализации поля) по сравнению с Vineflower (мощный existing
Java-декомпилятор) - тот даёт куда более идиоматичный, чистый код
(enhanced for-each, без лишних кастов, инлайн field-инициализация).

**ВАЖНО: это НЕ баг порта** - оригинальный Python `structure.py`/
`stackvm.py` УЖЕ не восстанавливает enhanced-for (только цикл с
Iterator как есть в байткоде) и не убирает "лишние" касты, которые в
байткоде явно присутствуют (checkcast инструкции) - это ОГРАНИЧЕНИЯ
САМОГО ОРИГИНАЛЬНОГО ДВИЖКА, унаследованные 1:1 моим портом
(корректно, я делал ЧЕСТНЫЙ 1:1 порт, не улучшение). Это ЗАДЕЛ на
будущее УЛУЧШЕНИЕ движка (не C++-порт, а НОВАЯ функциональность):
- Распознавание паттерна `Iterator it = X.iterator(); while(it.hasNext()) { T t = (T) it.next(); ... }`
  и сворачивание в `for (T t : X) { ... }`.
  - Убирание избыточных кастов, когда они гарантированно избыточны
  (напр. `(String) someStringExpr` когда `someStringExpr` УЖЕ имеет тип
  String по данным анализа типов).
- Слияние `static { FIELD = value; }` в `FIELD = value;` (инлайн), если
  static-блок присваивает поле РОВНО ОДИН РАЗ и больше ничего не делает.

Записано как backlog-идея для v2.x улучшений качества (после того как
C++ порт полностью закончен и стабилен) - НЕ реализовывать сейчас,
приоритет ниже, чем закончить порт.
