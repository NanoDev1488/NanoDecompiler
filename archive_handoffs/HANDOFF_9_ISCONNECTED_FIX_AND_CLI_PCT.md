# HANDOFF_9: CLI не показывал процент (мелкий фикс), и настоящий фикс
# if/else-бага (isConnected() из HANDOFF_7 Аддендум 13 - НАКОНЕЦ починен)

Продолжение HANDOFF_8 в той же сессии. Пользователь спросил, почему обычный
CLI-запуск (`main.py plugin.jar out_dir` без флагов) не печатает в консоль
процент "сколько методов декомпилировано", хотя `--json-output`/API-режим
его отдаёт (`decompiled_pct`).

## Фикс 1: CLI не печатал процент (main.py)

Причина: `write_readme()` считает и пишет статистику ТОЛЬКО в
README_RU.txt, обычный CLI-путь (`main()`, не `--json-output`) никогда не
делал `cprint()` этого значения в консоль - только "[*] README: путь".
Добавлена одна строка сразу после `write_readme()`:

    cprint(f"[*] Методов декомпилировано: {stats.decompiled_methods}/{stats.total_methods} ({pct:.1f}%)")

Тривиально, проверено - печатается корректно.

## Фикс 2: if/else-баг - настоящая причина, почему isConnected() НЕ
## подхватился фиксом из HANDOFF_8

В HANDOFF_8 фикс (`_find_forward_merge`) чинил ОБЩИЙ случай ("обе ветки
терминируют, `ipdom` не нашёл merge"), но конкретно `SQLite.isConnected()`
устроен ИНАЧЕ: там срабатывает старая XOR-эвристика (`t_term and not
f_term`), которая при `ipdom.get(false_t) is None` просто ставила
`merge = false_t` (адрес начала false-ветки) - НЕ пытаясь искать реальную
точку схождения вообще. Именно ЭТА эвристика (написана до текущей сессии,
до HANDOFF_7 даже) была настоящим виновником для isConnected(): она в
принципе не пыталась звать `_find_forward_merge`.

Трассировка (`NANO_DEBUG_IF`, временный debug-хук, убран из финальной
версии) подтвердила:

    pc=0  true_t=23 false_t=7  t_term=True f_term=False  (XOR-случай)
    pc=7  true_t=23 false_t=19 t_term=True f_term=True    (общий случай, уже чинился HANDOFF_8)

Фикс: в обеих ветках XOR (`t_term and not f_term` / `f_term and not
t_term`), если `ipdom.get(...)` вернул `None` - тоже пробуем
`_find_forward_merge` ПЕРЕД тем, как сдаться на старый дефолт
(`merge = false_t`/`true_t`).

### Побочная находка и её фикс: shared jump target ломает `min(common)`

При этом обнаружилось: `_find_forward_merge(true_t=23, false_t=7, ...)`
для pc=0 (XOR-случай) находит `common = {23, 24}` - потому что false_t=7
сам по себе if, одна из его веток ведёт РОВНО на 23 (тот же адрес, что и
true_t внешнего if - `connection.isClosed()` при true даёт тот же "return
false", что и `connection == null`). `min({23,24})` = 23 - НЕПРАВИЛЬНО:
23 - это САМ true_t, использовать его как merge даёт ПУСТОЕ then_body
(регион строится с 23 в стоп-сете, останавливается сразу на старте).

Исправлено: `_find_forward_merge` получил параметр `exclude_starts`
(по умолчанию `False`) - когда `True`, исключает `{true_t, false_t}` из
кандидатов в merge. Включается ТОЛЬКО в вызовах из XOR-веток (там true_t/
false_t - это КОНКРЕТНЫЕ адреса одного уже известного if, чужой shared-
target не может быть их собственным "продолжением после"). Общий вызов
(`if merge is None: merge = self._find_forward_merge(...)` - для случая
"обе ветки термально расходятся, но не связаны XOR-паттерном") оставлен
БЕЗ исключения - потому что там true_t/false_t ИНОГДА САМИ И ЕСТЬ
правильный merge (см. ниже).

**Это ловилось не с первого раза** - сначала включил `exclude_starts`
безусловно (для обоих типов вызова) - сломало `InventoryListener.
onInventoryClick` (регресс 293->291 методов, "переменная объявлена в
блоке" категория вернулась с 0 до 2). Разобрался через бисекцию (отдельно
откатывал каждое из двух добавленных изменений) - оказалось, безусловное
исключение ломает случаи, где merge должен буквально совпасть с true_t/
false_t самих по себе (не shared-target с ЧУЖИМ if, а просто "эта ветка
сама постдоминирует другую"). Разделил на `exclude_starts` параметр,
включаемый только там, где реально нужен.

## Итоговый результат на EryBuyer-v1.jar

    91.7% (289/315, до HANDOFF_8) -> 93.0% (293/315, после HANDOFF_8+9)

Полная построчная сверка (`diff -rq`) всех .java между "HANDOFF_8-финал" и
"HANDOFF_9-финал" - различается ТОЛЬКО `SQLite.java` (isConnected()
починен), остальные 6 файлов из HANDOFF_8 - без изменений (не
регрессировали). InventoryListener/MaterialHeadParser/SkullUtils - все
удержаны в починенном состоянии.

`SQLite.isConnected()` теперь:

    public boolean isConnected() {
        int __stk1;
        try {
            __stk1 = connection == null ? 0 : !connection.isClosed();
        } catch (SQLException var1) {
            return false;
        }
        return __stk1;
    }

Семантика ПРАВИЛЬНАЯ (NPE больше нет - `isClosed()` не вызывается, если
`connection == null`). НО остался отдельный, НЕ мой - см. ниже.

## НЕ мой баг, но замечен по пути: `int __stk1` при `return`-типе `boolean`

`_fold_boolean_materialization` (structure.py, сворачивает `if(cond) t=X;
else t=Y;` в `t = cond?X:Y;`) берёт тип результата из ТИПА КОНСТАНТЫ
литерала (`0` типизирован как `"int"`, а не `"boolean"`, потому что JVM
буквально хранит boolean как int - `iconst_0`/`iconst_1`). Отсюда
`int __stk1;` вместо `boolean __stk1;`, и `return __stk1;` при
объявленном `boolean isConnected()` - несовпадение типов, компилятор
откажет.

Проверено: это ПРЕДСУЩЕСТВУЮЩАЯ проблема, НЕ внесённая ни этим, ни
предыдущим фиксом - раньше (до HANDOFF_8/9, в самом первом baseline) тот
же дефект проявлялся ИНАЧЕ (`boolean __stk1; ... __stk1 = 0;` - тоже не
компилируется, там 0 типизирован как int, а переменная как boolean).
Просто раньше линия с ошибкой была assignment, теперь - return. Ни
лучше, ни хуже с точки зрения "компилируется или нет" - в обоих случаях
не компилируется. НЕ чинил в этой сессии - корень в том, как типизируются
int-константы 0/1, используемые как boolean (вероятно где-то в
stackvm.py при симуляции `iconst_0`/`istore` в слот, который используется
как boolean - тип нужно тянуть либо из объявленного типа переменной, либо
из контекста использования, а не из самого литерала). Следующей сессии
стоит поискать по всем местам, где Const создаётся с типом "int" для
значений 0/1, которые потом используются как boolean.
