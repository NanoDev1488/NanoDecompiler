# HANDOFF_5: AES-строки, приёмы именования, catchclean, критический баг установщика, апдейтер движка

Продолжение HANDOFF_1-4. В этой сессии - разбор реального Windows-теста
(видео + скрины), порт логики с Rust-инструмента пользователя, и бэкенд
апдейтера движка.

## КРИТИЧЕСКИЙ БАГ - "Установщик завершился без ответа" - ПОЧИНЕН

Пользователь показал скрины/видео реального теста на Windows: декомпиляция
отрабатывала на 100% нормально, но кнопка "Установить недостающее? Да/Нет"
(java/maven) падала с "Установщик завершился без ответа - см. вывод
декомпиляции для деталей". Это ЖЕ было тем самым "сломалась прога" из
отдельной жалобы - один баг, не два.

**Причина**: `toolinstaller.py::_well_known_dirs()` вызывала `os.listdir()`
на путях типа `C:\Program Files\Java` БЕЗ `try/except`. На реальной
Windows-машине это может бросить `PermissionError`/`OSError` (антивирус
держит папку, OneDrive-заглушка и т.п.) - и падало ВООБЩЕ ДО того, как
что-либо печаталось в JSON. `install_missing()` при этом ловил только
`ToolInstallError`, не любой `Exception` - так что баг проходил насквозь
до самого верха и электрон получал пустой stdout.

**Починено в 4 местах**:
1. `os.listdir()` в `_well_known_dirs()` (2 места) и `_find_one()` - теперь
   в `try/except OSError`, просто пропускает проблемную папку.
2. `install_missing()` теперь ловит `Exception` целиком, не только
   `ToolInstallError`.
3. `main.py::_try_handle_install_tools_json()` - вся логика обёрнута в
   `try/except`, гарантированно печатает `{"type":"error","message":...}`
   при ЛЮБОМ неожиданном исключении внутри.
4. `electron/main.ts` - `ok` в ответе раньше был жёстко `true` ВСЕГДА
   (даже при непустом `errors[]`) - починено на `finalResult.errors.length === 0`.

Проверено: симуляция реального `PermissionError` внутри `os.listdir` на
живом коде - раньше падало бы необработанным, теперь корректно
восстанавливается и печатает понятную JSON-ошибку. Полная регрессия на
всех 15 jar - без изменений.

## Порт Rust-деобфускатора пользователя (deobfuscator-rust.zip)

Внимательно разобрал структуру (`decryptor.rs`, `crypto.rs`, `names.rs`,
`catchclean.rs`, `deadcode.rs`, `junk.rs`). Из них перенёс на Python (с
адаптацией под наши структуры данных, НЕ дословный порт):

### 1. Расшифровка строк для ОДНОЙ конкретной схемы обфускатора

`aes128.py` (AES-128 с нуля, чистый Python - **проверено на официальном
NIST FIPS-197 тестовом векторе**, совпадает побайтово) + `str_decrypt.py`
(узнавание схемы: маркер `"AES/ECB/PKCS5Padding"` в constant pool + два
int-поля h/l -> SHA-256 -> первые 16 байт ключ -> AES-128-ECB+PKCS7).

Подключено в `stackvm.py` на уровне `invokestatic`: если для этого jar'а
найден расшифровщик (пре-скан в `main.py` перед основным циклом,
результат в module-level `str_decrypt.ACTIVE` - НЕ через проброс параметра
через 4 места вызова `decompile_method_body`, т.к. обработка строго
последовательная, без потоков) - вызов ИМЕННО на этот метод с константным
строковым аргументом заменяется на расшифрованный литерал. Если что-то не
сходится - падает через в обычную обработку, никакого угадывания.

Добавлен `Const.raw` (ast_nodes.py) - сырая нешифрованная строка рядом с
уже готовым Java-литералом, чтобы не откатывать экранирование обратно.

ПРОВЕРЕНО: полный pipeline (маркер -> ключ -> расшифровка) на синтетическом
но точном по структуре `ClassFile`-объекте - совпадает побайтово с
зашифрованным вручную (тем же AES) эталоном. НЕ проверено на реальном jar'е
с этой точной схемой - ни один из 15 доступных jar её не использует
(ожидаемо - это конкретная, не самая частая схема).

⚠️ Это НЕ общий "исполни произвольный decrypt-метод в песочнице" (то, что
предыдущая сессия планировала как безопасный, но не сделанный пункт 2) -
это узнавание ОДНОЙ конкретной, зафиксированной схемы. Общий безопасный
случай (исполнение чистого метода с константными аргументами) остаётся
несделанным - более рискованная задача, требует отдельной сессии.

### 2. Приёмы именования (не общий type-based, а контекстные - см. names.rs)

`naming_hints.py`:
- `by_annotation_name()` - если >=3 разных класса несут одну и ту же
  аннотацию с текстовым аргументом "name" (самодельный DI/модульный
  фреймворк) - берём это имя вместо `ClassA{N}`.
- `by_brigadier_super_call()` - специфично для Minecraft/Brigadier: если
  проект использует Brigadier (маркер в constant pool) и обфусцированный
  класс расширяет тоже обфусцированный класс, а `<init>` начинается ровно
  с `aload_0; ldc "строка"; invokespecial <super>.<init>` - строка - имя
  команды, класс переименовывается в `Command{Имя}`.

Подключено в `Renamer.friendly_class` (main.py) как `class_name_hints`
dict - используется ТОЛЬКО когда обычная эвристика уже решила, что имя
обфусцировано, и только для последнего сегмента (не для Outer$ обёрток).

ПРОВЕРЕНО: регрессия на 15 jar - без изменений (ни один не использует ни
Brigadier с обфусцированными командами, ни аннотационный DI - ожидаемо для
небольших плагинов). Логика проверена, живой срабатывания пока не видели.

### 3. Удаление мусорных catch-and-rethrow блоков

`catchclean.py` - находит exception-table записи, чей handler - ТОЧНО
`astore S; aload S; athrow` или голый `athrow` (семантически no-op catch,
частый обфускаторский шум). Подключено в `engine.py` перед построением CFG
и Structurer - использует ОТФИЛЬТРОВАННЫЙ список exceptions в обоих местах.

БЕЗОПАСНО ПО КОНСТРУКЦИИ: catch-and-rethrow функционально прозрачен,
удаление не меняет поведение программы.

ПРОВЕРЕНО живьём: сработало на 4 из 15 реальных jar (AEXF: 8, ajLeaderboards:
9, antirelog: 5, huinya: 11 - итого 33 мусорных catch-блока убрано).
Юнит-тесты на синтетическом байткоде - все прошли. Небольшие колебания
процента декомпиляции на этих 4 jar (±0.02-0.05%) - проверено через
`fallback_reasons`, никаких новых/необычных категорий ошибок не появилось,
в пределах шума от смещения границ блоков.

## Бэкенд апдейтера движка (electron/updater.ts)

Пользователь уточнил: движок УЖЕ отдельный `.exe` внутри клиента (не
встроен в сам процесс) - обновление = скачать новый `NanoDecompilerAPI.exe`
и заменить старый, без сложного "частичного патча".

Реализовано:
- `update:check` (IPC) - опрашивает GitHub Releases API
  (`api.github.com/repos/{owner}/{repo}/releases/latest`), сравнивает тег
  с текущей версией движка (`ENGINE_VERSION` в `updater.ts`).
- `update:apply` (IPC) - скачивает asset `NanoDecompilerAPI.exe`, атомарно
  заменяет (`.download` -> `fs.renameSync`, не оставляет битый файл на
  середине скачивания).

НЕ СДЕЛАНО: кнопка/экран в `App.tsx` - бэкенд готов, дёргать его пока
некому. Плюс нюанс: сейчас единый релиз (тег `v1.2`) содержит И клиент, И
движок вместе (см. `build-and-release.yml`) - апдейтер сравнивает
`ENGINE_VERSION` с `tag_name` релиза ЦЕЛИКОМ, что немного не то (движок и
клиент версионируются независимо по замыслу) - если разделять теги
обратно на `client-vX`/`api-vY` (как было до объединения в один релиз с
текстом) - апдейтер тогда стоит смотреть по `api-vY` конкретно, не по
общему тегу. Стоит решить это до реального использования апдейтера.
