## НЕ начато (осталось из волны 5/7, по-прежнему честно, не выдумываю)

- **Host-reachability для Modrinth/SpigotMC** (различать "источник
  недоступен/заблокирован" от честного "ничего не найдено"). Разобрался
  глубже в этой волне: `check_site()` УЖЕ отчасти это умеет -
  `out.checked` остаётся `false`, если `http_get`/`http_get_json` вообще
  не вернул валидный ответ (сетевая ошибка/таймаут curl). Проблема ИМЕННО
  в подозрении на гео-блокировку: типичный гео-блок отдаёт HTTP 200 с
  пустой/redirect-страницей, а НЕ curl-уровня сбой - в этом случае
  `checked` некорректно останется `true` (данные пришли, просто "ничего
  не нашли"), хотя на самом деле источник недоступен ИЗ-ЗА
  блокировки. Не реализовывал вслепую: чтобы отличить "пустой, но
  валидный ответ API" от "блокировочная страница, которая ВЫГЛЯДИТ как
  200 OK", нужен либо (а) сигнатурный список типичных ответов
  гео-блокировщиков конкретно для Modrinth/SpigotMC (нужен реальный
  пойманный пример такого ответа - его тут никто не видел), либо (б)
  отдельный лёгкий пробинг известного стабильного ресурса на том же
  хосте ДО основного запроса - оба варианта решают проблему лишь
  частично и требуют явного решения пользователя, какой компромисс
  приемлем, а не тихой догадки агента.
- Остальное без изменений: языковые файлы + `--lang`, `ChatColor.RED`-
  чипы (ждём .jar), группы кнопок "ярлычки-стрелочки" (нужна конкретика).

## Про "нон-стоп волны" (важно для следующего агента И для человека)

Пользователь в этой сессии явно попросил делать волны 1.9.12/13/14 подряд
без дополнительных вопросов. Волна 8 (эта) сделала ОДИН реально готовый,
полностью проверяемый пункт (GUI-wiring выше). Для волны 9/10 на этот
момент **не осталось конкретно сформулированных, ещё не сделанных
жалоб** - только host-reachability (см. выше, сознательно не начат
вслепую) и три пункта, явно требующих либо .jar от пользователя, либо
уточнения формулировки ("ярлычки-стрелочки"). Штамповать версии дальше
без реального содержания было бы ровно тем "выдумыванием прогресса",
против которого прямо предостерегают комментарии в этом же кодовом
проекте (см. `legitimacy_check.hpp`: "НЕ выдумываю прогресс"). Правильный
следующий шаг - спросить пользователя, что делать с host-reachability
(вариант а/б выше) и есть ли новые жалобы, а не продолжать генерировать
версии ради версий.
