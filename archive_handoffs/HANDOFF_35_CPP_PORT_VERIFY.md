### Важные детали порядка (Python dict = порядок вставки)

`check_import_collisions` и `ProjectStats.fallback_reasons` в оригинале -
обычные Python-словари, для которых порядок ВСТАВКИ гарантирован (3.7+) и
влияет на порядок вывода (`summary_text` берёт первые 30/40 элементов и
показывает их в этом порядке; группировка причин отката сортируется по
убыванию count, но при РАВНОМ count порядок - порядок первого появления,
т.к. `sorted()` в Python устойчив). В C++ `std::map` СОРТИРОВАЛ бы по
ключу и незаметно поменял бы этот порядок - вместо этого использованы
`OrderedImportMap`/`ImportConflicts` (`std::vector<std::pair<...>>`) и
`fallback_reasons` тоже как order-preserving `vector<pair<...>>`, с явным
линейным поиском при инкременте (как `dict.get(key,0)+1`, только с
сохранением порядка вставки).

### Найденный нюанс в `check_brackets` (сохранён как есть, это ОСОБЕННОСТЬ
### оригинала, не баг порта)

Экранирование `\` внутри строк/символьных литералов делает `i += 2`
(пропускает следующий символ БЕЗ проверки, не перевод ли строки) - то есть
если экранированный символ - это `\n` (маловероятно внутри одной Java
строки, но теоретически возможно в многострочных текстовых блоках Java
15+, которые этот примитивный лексер не отличает от обычных строк),
счётчик строк для диагностики собьётся на такой строке. Не исправлено -
это поведение оригинала, а не баг порта; отмечено на будущее.

### Регрессия

Сверено на: 9 сценариев `check_brackets` (простой сбалансированный код,
скобки внутри строкового/символьного литерала, внутри `//`- и `/* */`-
комментария, лишняя закрывающая скобка, незакрытая скобка, несовпадение
типов скобок, экранированная кавычка внутри строки) - **точное
совпадение** сообщений об ошибках (включая номера строк); коллизии
импортов на 5 записях с 2 коллизиями - **точное совпадение**; и полный
`summary_text()` на реалистичном наборе статистики (98 методов, 3 разные
причины отката, библиотечные классы, коллизии импортов, ошибки парсинга) -
**побайтовое совпадение** всего многострочного отчёта (после того как
тестовый Python-скрипт сначала неверно добавлял свой лишний `\n` через
`print()`, а не `sys.stdout.write()` - артефакт тестовой обвязки, не
порта, тут же исправлено и пересверено).
