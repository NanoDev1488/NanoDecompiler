# NanoDecompiler v1.4 — changelog

Сессия фокусировалась на движке декомпиляции (`resources/engine`). Все
фиксы проверены на реальных .jar (EryBuyer + 11 других — NanoSpec,
NanoQuests, NanoRTP, DeluxeMenuConstructor, ChatFilterPlus, Salaires,
WorldGuard-Translator, MSG, rccooldown, HeadDatabase, TowerClans,
FunnyClans), не на синтетике.

## Основные фиксы

**"Нередуцируемый переход внутри региона" (крупнейшая оставшаяся категория)**
Классический `for (Entry e : map) { if (cond) continue; ... }`. Постдоминатор
честно вычислял заголовок ОБЪЕМЛЮЩЕГО цикла как "точку после if" (все пути
туда рано или поздно возвращаются) — но использовать его как обычное
продолжение нельзя, это `continue`. Движок пытался повторно построить уже
строящийся заголовок цикла и падал. Крупнейший прирост за сессию:
EryBuyer 93.0% → **97.8%**. Заодно нашёл и починил сопутствующий баг —
дублирующиеся объявления переменных (`int allSkipped;` дважды в одном
методе), когда один JVM-слот переиспользуется под одну переменную в двух
независимых ветках.

**Косметическая чистка temp-переменных**
Рекурсивный фикс пересечения стека (ниже) давал корректный, но
многословный код — по несколько `__stkN` на каждый уровень цепочки.
Добавлены три прохода очистки (схлопывание цепочек копирований, вынос
идентичных "хвостов" из обеих веток if/else, подстановка одноразовых
temp прямо в место использования). Пример:
`Player __stk1; ... if(...){...} __stk5.setAutobuyer(__stk4,__stk3);`
→ `setAutobuyer(player, !isAutobuyerEnabled(player));`. Проверено на
всех 12 jar — числа декомпиляции не изменились (чистая косметика), diff
показал только читаемость.

**If/else-баг (структуризатор)**
Когда обе ветки `if/else` завершались (return/throw) РАЗНЫМИ путями,
точка схождения терялась, и вместо вложенного `if/else-if` получались
два независимых соседних `if`. Добавлен поиск реальной точки схождения
по CFG вместо чистого доверия дереву доминаторов (которое сбивают
рёбра исключений).

**CLI не показывал процент декомпиляции**
`--json-output`/API режим отдавали `decompiled_pct`, обычный CLI-запуск
— нет (только прятал в README_RU.txt). Теперь печатает в консоль как
и API.

**"Двойной" try/catch с одинаковыми типами исключений**
Оказался не настоящей вложенностью — javac иногда режет ОДИН логический
`try`-блок на несколько смежных диапазонов в exception-table (нашли
ровно такой случай — `return` посреди try, не бросающий исключений,
исключён из защищённого диапазона). Сшивается обратно перед построением
try/catch.

**int/boolean-типизация**
JVM хранит `boolean` как `int` (`iconst_0`/`iconst_1`). Из-за этого при
свёртке `if/else` в тернарник или при возврате из crossing-переменной
получались `int __stkN;` / `return 0;` при объявленном `boolean`-методе
— не компилировалось. Починено в двух местах (свёртка тернарника и
инференс типа сквозных переменных).

**"Многозначное пересечение стека" (arr[i] = cond ? a : b и подобное)**
Самая массовая из оставшихся категорий отката. Механизм сведения
значений, пересекающих границы блоков, был однопроходным — не видел,
когда значение (например `this`) проходит НЕ через один, а через
НЕСКОЛЬКО блоков подряд не потребляясь. Реконсиляция стала рекурсивной.

## Не починено (задокументировано для следующей сессии)

- **var7/slot-reuse баг** (`SQLite.getPlayerData()`) — JVM легально
  переиспользует один local-slot под разные типы (`PlayerLevel` /
  `Throwable`) в suppressed-exception ветке try-with-resources. Попытка
  точечного фикса заменила компиляционную ошибку на ТИХИЙ семантический
  баг (самоссылка `e2.addSuppressed(e2)`) — откачена. Нужен
  pattern-matcher на форму try-with-resources целиком, не патч поверх
  именования catch-переменных.
- **`DeluxeMenuConstructor.loadMenu()`** — падает с тем же классом ошибки
  ("несогласованная глубина"/переход), но ни фикс пересечения стека, ни
  фикс заголовка цикла его не берут; крупный метод со стримами/лямбдами,
  не разбирался глубоко.
- Остальные категории отката не трогались: "нередуцируемый goto",
  "synchronized-блок не свёрнут".

Подробная техническая документация каждого фикса — в
`HANDOFF_8`…`HANDOFF_15` внутри архива движка.
