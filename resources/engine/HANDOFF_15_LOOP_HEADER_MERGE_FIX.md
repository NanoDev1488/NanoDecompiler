# HANDOFF_15: "нередуцируемый переход внутри региона" - главный виновник
# найден и починен (плюс сопутствующий дедуп-баг объявлений)

Продолжение HANDOFF_14. Самая крупная из оставшихся категорий отката (11
случаев в EryBuyer, много больше по остальным jar).

## Диагностика: repro на bStats `getChartData()`

Классический `for (Entry e : map.entrySet()) { if (e.getValue() <= 0)
continue; ...; }`. Байткод: заголовок цикла (hasNext-проверка, pc=51),
внутри тела - `if` (pc=61) с true_t=92 (обработать элемент, в конце
`goto 51`) и false_t=89 (`goto 51` напрямую - это и есть `continue`).

Через отладочную трассировку (`region()`, `_build_if_inner` - временные
хуки, убраны из финальной версии) нашёл: `ipdom.get(61)` возвращает
**51 - заголовок ОБЪЕМЛЮЩЕГО цикла**. Математически это ЧЕСТНЫЙ ответ
(все пути от pc=61, даже длинные, рано или поздно возвращаются в 51 -
значит 51 действительно единственный узел, через который проходят ВСЕ
пути) - но использовать его как "точку продолжения ПОСЛЕ if" нельзя: код
тела цикла уже строится ОТДЕЛЬНЫМ вызовом `region()` (см. `_build_loop`)
- попадание туда изнутри if это `continue`, а не обычное линейное
продолжение сканирования. `region()` пытался повторно построить уже
строящийся заголовок цикла и падал.

## Фикс (structure.py, `_build_if_inner`)

Один guard непосредственно перед использованием `merge`: если merge (из
ЛЮБОГО источника - сырой `ipdom` или любая из эвристик-фоллбэков)
совпадает с заголовком АКТИВНОГО (уже входящего в `self.loop_stack`)
цикла - считаем, что слияния нет (`merge = None`), и полагаемся на уже
существующий механизм: обе ветки строятся через `_resolve_jump_stmt`,
который корректно распознаёт `goto <header>` как `continue`.

## Побочная находка: дублирующиеся объявления переменных

При проверке всплыл ОТДЕЛЬНЫЙ баг: `int allSkipped;` объявлялась ДВАЖДЫ
в одном методе (не компилируется). Причина - `_hoist_escaping_locals`
(engine.py) поднимает объявление переменной над блоком, где она
эскейпит область видимости, НО делает это НЕЗАВИСИМО для каждой ветки
метода - если ОДИН И ТОТ ЖЕ JVM-слот используется как одна и та же
логическая переменная в ДВУХ независимых местах метода (например
счётчик, настраиваемый в `if` до цикла и снова изменяемый в `if` внутри
цикла), каждое место хоистит СВОЁ объявление.

Починено: `_hoist_escaping_locals` теперь принимает (и прокидывает через
всю рекурсию) общее множество `_declared_so_far` - объявление
эмитится только для имён, ещё не объявленных РАНЕЕ где-либо в этом же
методе; повторные "эскейпы" того же имени по-прежнему конвертируют
внутренний `LocalDecl` в присваивание (иначе тоже дублирование), просто
не эмитят вторую верхнеуровневую декларацию.

Проверено (специальный тест): временно откатил HANDOFF_14 (косметику) -
дубль остался, значит это НЕ побочный эффект косметической чистки, а
самостоятельный, ранее скрытый баг - просто раньше НИ ОДИН метод не
доживал до этого сценария (либо аборт по "нередуцируемый переход",
либо иначе).
