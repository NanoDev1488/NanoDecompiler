## Реализовано: find_active_decryptor_in_jar

Новая функция в `str_decrypt.hpp/cpp`, переносящая ТОЧНЫЙ протокол из
`main.py` строк 737-753 (единственный ещё не перенесённый кусочек логики,
нужный именно для этой задачи - не весь `main.py`, узкий кусок под
конкретный запрос):
- перебирает классы **в порядке их появления в jar** (порядок важен - как
  `zip.namelist()`/`class_files.items()` в Python, где словарь сохраняет
  порядок вставки);
- ищет первый класс с маркером расшифровщика (`find_decryptor_in_class`);
- **важный нюанс, воспроизведённый точно**: как только найден класс с
  маркером (даже если это НЕ дало действительный ключ - т.е. `key` найден),
  поиск ОСТАНАВЛИВАЕТСЯ, НЕЗАВИСИМО от того, нашёлся ли у этого класса
  подходящий метод `decrypt_method_name` - в оригинале `break` стоит вне
  `if _decrypt_method:`, но внутри `if _key:`. Если метод не нашёлся,
  функция возвращает `nullopt` (ничего не активируется), но дальше по jar
  уже не ищет - легко было упустить эту деталь (естественным было бы
  "продолжать искать, пока не найдём ПОЛНОЕ совпадение").

## Сквозная проверка (полный протокол, реальная AES-схема)

Написан офлайн-генератор синтетических `.class`-файлов (чистый Python,
`struct`, без внешних зависимостей - имитирует РЕАЛЬНУЮ схему обфускатора):
1. `Decryptor.class` - класс с маркером `"AES/ECB/PKCS5Padding"` (как
   осиротевшая запись constant pool - валидно для реального формата class-
   файла), двумя `public static final int` полями `h`/`l` с
   `ConstantValue`, методом `public static String decrypt(String)`.
2. `Main.class` - вызывает `Decryptor.decrypt(...)` с Base64-строкой,
   зашифрованной РЕАЛЬНЫМ AES-128-ECB+PKCS7 (через стороннюю
   `cryptography`, только для генерации тестовых данных) тем самым ключом,
   что выводится из `h`/`l` через `build_key` (SHA-256).

Прогон полного пайплайна (`find_active_decryptor_in_jar` ->
`str_decrypt_set_active` -> `simulate_block` на методе `Main.getSecret()`):

```
найден расшифровщик: owner=com/evil/Decryptor method=decrypt
return "https://discord.com/api/webhooks/111111/SUPER_SECRET_TOKEN";
decrypted_count=1
```

Проверено на **точное совпадение** с тем же сценарием через ОРИГИНАЛЬНЫЙ
Python-движок (`str_decrypt.py`+`stackvm.py`+`emit.py`) - тот же `owner`/
`method`, тот же расшифрованный литерал, тот же `decrypted_count`.

Дополнительно - защита от ложных срабатываний: `find_active_decryptor_in_jar`
прогнана на **всех 4075 классах из всех 13 джарников пользователя** (все
легитимные, не зашифрованные плагины) - **ни одного ложного
срабатывания**, как и ожидается.

## Итог

Полный путь "runtime-деобфускация зашифрованных строк/ссылок" - от

подтверждён побитовым совпадением с оригинальным движком на реалистичном
сценарии (настоящее AES-шифрование, настоящая Discord-webhook-ссылка как
пример).
