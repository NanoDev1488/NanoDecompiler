# NanoDecompiler v1.4.2

Полноценный декомпилятор байткода Java для Bukkit/Spigot-плагинов. Не просто
дизассемблер — парсит `.class`-файлы вручную, строит граф потока управления,
символически исполняет байткод и **структурирует** его обратно в читаемый
Java (if/else, while/do-while/for, switch, try/catch — без единого `goto`).

Чистый Python 3, stdlib. Работает одинаково на Windows и в Termux (Android).

На реальном корпусе из 12+ сторонних плагинов (не синтетика) движок сейчас
восстанавливает **90–100% методов** в структурированный, компилируемый Java
(конкретные цифры — см. раздел [Тестирование / регрессия](#тестирование--регрессия)).

## Что нового в v1.4

Крупный проход по движку структуризации (`structure.py`/`engine.py`),
проверенный на 12+ реальных сторонних плагинах (не синтетика). Кратко (всё
подробно — в `HANDOFF_8_...md` … `HANDOFF_15_...md` и в
`CHANGELOG_v1.4.md`):

- Починен if/else-баг структуризатора (терялась точка схождения, когда обе
  ветки завершались `return`/`throw` разными путями).
- CLI теперь печатает процент декомпиляции в консоль (раньше это отдавал
  только `--json-output`/API).
- «Двойной» `try`/`catch` с одинаковыми типами исключений — оказался не
  вложенностью, а разрезанным javac диапазоном в exception-table; сшивается
  обратно.
- Исправлена типизация `boolean`-констант, которые JVM хранит как `int`
  (`0`/`1`) — убирает несовпадения типов при компиляции.
- Общий механизм пересечения стека между блоками (тернарники,
  `arr[i] = cond ? a : b` и т.п.) стал рекурсивным вместо однопроходного —
  чинит случаи, когда значение проходит НЕ через один, а через несколько
  блоков подряд не потребляясь.
- Добавлена косметическая чистка временных `__stkN`-переменных, которые
  оставлял предыдущий пункт — компилировалось и раньше, но было многословно.
- Починена САМАЯ массовая категория отката («нередуцируемый переход внутри
  региона») — постдоминатор корректно видит заголовок цикла как общую
  точку схождения, но использовать его как обычное продолжение (а не
  `continue`) неверно. Заодно найден и починен смежный баг с дублирующимися
  объявлениями переменных.

Итог на самом прогоняемом тестовом jar (`EryBuyer-v1.jar`): **91.7% →
97.8%** методов полностью восстановлены. На корпусе из 9 дополнительных
сторонних плагинов — от +1 до +35 методов на каждый, без единой регрессии
(проверено построчным diff'ом вывода до/после на каждом фиксе).

Известные открытые проблемы после v1.4 — см. раздел
[Известные ограничения](#известные-ограничения).

## Что это и чего НЕ делает

**Делает:**
- Парсит constant pool, поля, методы, атрибут `Code`, `LocalVariableTable`,
  аннотации (`RuntimeVisible/InvisibleAnnotations` + параметры),
  `BootstrapMethods` (лямбды/method references), `InnerClasses`.
- Строит CFG (граф потока управления) из инструкций байткода + таблицы
  исключений.
- Символически исполняет каждый метод как стек-машину, восстанавливая
  выражения: арифметика, вызовы методов, `new`, касты, конкатенация строк,
  инкременты, тернарники, лямбды и method references.
- **Структурирует** управляющий поток через дерево доминаторов/
  постдоминаторов в `if`/`else`, `while`/`do-while`/`for`, `switch`
  (включая `switch(String)` через паттерн `hashCode`+`equals`), `try`/`catch`.
- Деобфусцирует имена классов/методов/полей/пакетов (мусорные короткие
  имена → читаемые: `ClassA1`, `method3`, `field7`, `pkg2`...) —
  консервативно, не трогает то, что и так похоже на осмысленное имя.
- Определяет и вычленяет известные шейднутые библиотеки (JDBC-драйверы,
  JSON/YAML, логирование, HTTP-клиенты и т.д., включая релоцированные через
  maven-shade `<relocations>`) — не декомпилирует их, а прописывает как
  обычную maven-зависимость в сгенерированном `pom.xml`.
- Генерирует `pom.xml`, `MAPPING_RU.txt` (было → стало) и `README_RU.txt`
  с отчётом и статистикой точности прямо в папке результата.

**Принципиально НЕ делает:**
- **Никогда не печатает код, в котором не уверен на 100%.** Если для
  конкретного метода встретился непривычный/редкий паттерн байткода —
  декомпилятор откатывается на честный дизассемблированный листинг именно
  для этого метода (с пояснением-комментарием), а не гадает и не выдаёт
  код, который может быть неверным. Остальные методы это не затрагивает.
  Это ключевой архитектурный принцип: лучше «не смог», чем «соврал».
- Не декомпилирует чужой закрытый код общего назначения (например, код
  самого Minecraft/Mojang) — только сторонние плагины поверх публичного
  Bukkit/Spigot API.

## Быстрый старт

**Linux / macOS / Termux:**
```bash
python3 main.py plugin.jar [output_dir]
```
Если `output_dir` не указан — создаётся `<имя_jar>_decompiled` рядом.

**Windows (движок, консоль):**
Перетащи `.jar`-файл на `run.bat` (или собранный `NanoDecompilerCLI.exe`)
— декомпиляция запустится в консоли с этим jar как аргументом. Двойной
клик БЕЗ перетаскивания файла просто печатает usage (это консольный
движок, не GUI — см. ниже).

**Windows (графический интерфейс):**
Отдельное приложение — `NanoDecompiler-Client-Setup.exe` (Electron), см.
раздел [GUI](#gui-windowsmacoslinux) ниже.

## Режимы запуска

### CLI (Linux/macOS/Termux)

```bash
python3 main.py plugin.jar [output_dir]
```
Печатает цветной прогресс, баннер, проверку окружения (java/maven) и
итоговую статистику. Результат — папка с исходниками `.java`, `pom.xml`,
`MAPPING_RU.txt`, `README_RU.txt`.

### GUI (Windows/macOS/Linux)

Отдельное приложение — Electron + React (`electron/`, `src/App.tsx`),
собирается инсталлятором под Windows (см. раздел
[Сборка в .exe](#сборка-в-exe-windows)); сам движок при этом запускается
как обычный дочерний процесс (`python3 main.py ... --headless`, либо
собранный `NanoDecompilerCLI.exe`).

Один тёмный терминал-стиль оформления (без переключения тем — старая
система с тремя Tkinter/Flet-темами, описанная ниже в списке файлов как
`gui_raw.py`/`gui_neon.py`/`gui_md3.py`, полностью удалена, см.
`HANDOFF_4_ELECTRON_AND_FIXES.md`). Возможности клиента:

- Drag-and-drop или выбор `.jar` файла, автоматическая сводка (размер,
  версия Java, число классов/пакетов) до запуска декомпиляции.
- Живой лог декомпиляции с подсветкой строк, инлайн-предложение поставить
  недостающие `java`/`maven` прямо по месту в логе.
- Автопроверка обновлений (движка и самого клиента отдельно — см.
  `electron/updater.ts`), кнопка «Обновить» / «Скачать и установить».
- Кнопка «Открыть в VS Code» для результата.
- **Настройки** (значок ⚙ в шапке, с v1.4.2 — раньше не было вообще):
  тумблер проверки легитимности (GitHub/Modrinth/SpigotMC/RuSpigot) и
  тумблер автопроверки обновлений. Хранятся в
  `<userData>/settings.json` (`app.getPath("userData")` — на Windows это
  `%APPDATA%\NanoDecompiler`).

`electron/main.ts` — главный процесс (IPC-хендлеры, спавн движка,
настройки); `electron/preload.ts` — мост в рендерер (`window.nano.*`);
`electron/updater.ts` — логика автообновления; `src/App.tsx` — весь UI
одним компонентом.

### API-режим (для интеграции с другими приложениями)

Два варианта — можно использовать любой или оба сразу.

**Разовый вызов, JSON в stdout:**
```bash
python3 main.py plugin.jar [out_dir] --json-output
```
Печатает **только** JSON (без баннера/цвета/прогресс-бара), код возврата
`0` (успех) или `1` (ошибка). Пример ответа:
```json
{
  "status": "ok",
  "out_dir": "plugin_decompiled",
  "elapsed_sec": 0.37,
  "stats": {
    "classes_total": 167,
    "classes_parsed": 167,
    "decompiled_methods": 296,
    "fallback_methods": 22,
    "decompiled_pct": 93.08,
    "fallback_reasons": { "...": 11 },
    "import_conflicts": { "Entry": ["a.b.Entry", "c.d.Entry"] },
    "library_names_hit": ["org.xerial:sqlite-jdbc"]
  }
}
```

**HTTP-сервер (stdlib `http.server`, без сторонних зависимостей):**
```bash
python3 main.py --api-server [--host 127.0.0.1] [--port 8791]
```
- `POST /decompile` — тело запроса: JSON `{"jar_path": "...", "out_dir": "..."}`
  ИЛИ сырые байты `.jar` напрямую (`Content-Type: application/java-archive`
  или `application/octet-stream`, опционально `?out_dir=...` в query-строке).
- `GET /health` — проверка живости.

**Гарантия:** в API-режиме GUI никогда не импортируется и не открывается —
даже на Windows, даже без аргументов. Проверяется первой строкой в
`main()`, до ветки `platform.system() == "Windows"`.

⚠️ Сервер слушает `127.0.0.1` по умолчанию — аутентификации/токена нет,
это рассчитано на локальную интеграцию. Если когда-нибудь понадобится
слушать не только localhost — обязательно добавить токен в заголовок.

## Установка Java/Maven по требованию

Проверка окружения (`java`/`mvn`) происходит перед декомпиляцией
автоматически и ничего не ставит сама — только сообщает, чего не хватает.

Если чего-то нет — можно поставить одной командой, **portable, без прав
администратора**, в локальную папку рядом с настройками (никак не трогает
системный `PATH`):

```bash
python3 main.py --install-tools            # поставит и JDK, и Maven, если не хватает
python3 main.py --install-tools=jdk        # только JDK
python3 main.py --install-tools=maven      # только Maven
```

- JDK — Eclipse Temurin (Adoptium API), LTS-версия 17.
- Maven — последняя стабильная версия с `dlcdn.apache.org`.
- Устанавливается в `%LOCALAPPDATA%\NanoDecompiler\tools` (Windows) или
  `~/.nanodecompiler/tools` (Linux/Termux).
- Проверка окружения потом видит эту папку сама, даже если `java`/`mvn`
  так и не попали в системный `PATH`.

На Windows проверка также умеет находить java/maven, установленные, но ещё
не подхватившиеся текущим процессом (классическая ситуация «поставил — а
PATH обновится только после перезагрузки») — читает актуальный `PATH` прямо
из реестра и проверяет типичные пути установки (`JAVA_HOME`, `MAVEN_HOME`,
`Program Files\...`, scoop).

## Что на выходе

В указанной папке результата:
- `src/...` (или аналогичная структура пакетов) — восстановленные `.java`.
- `pom.xml` — сгенерированный/восстановленный, с зависимостями на известные
  шейднутые библиотеки.
- `MAPPING_RU.txt` — таблица «было → стало» для всех переименованных
  классов/методов/полей/пакетов.
- `README_RU.txt` — отчёт: сколько методов восстановлено полностью, сколько
  ушло в честный fallback на байткод и почему, коллизии импортов, найденные
  библиотеки, общая оценка «крутизны» декомпиляции.

## Как это работает (архитектура)

Плоская структура — все `.py`-файлы в одной папке, без пакетов:

```
main.py         оркестрация (process_jar/process_jar_with_stats), CLI/GUI
                entry point, консольный вывод, проверка java/maven,
                детект известных библиотек и релокаций
classfile.py    парсер .class (constant pool, поля, методы, Code,
                LocalVariableTable, аннотации, BootstrapMethods, InnerClasses)
ir.py           декодирует сырой байткод в список инструкций
cfg.py          строит CFG из инструкций + таблицы исключений
stackvm.py      символическое исполнение блока: байткод -> дерево выражений
engine.py       decompile_method_body() - весь пайплайн одного метода,
                все проверки DecompileAbort
structure.py    CFG -> структурированное дерево (if/while/for/switch/try)
emit.py         AST -> текст Java
ast_nodes.py    узлы AST
javatypes.py    дескрипторы JVM -> Java-типы, эвристика "похоже на обфускацию"
pom_builder.py  генерация pom.xml, таблица известных библиотек
verify.py       статистика точности, баланс скобок, коллизии импортов
switchmap.py, disassembler.py, opcodes.py   вспомогательные модули
toolinstaller.py   portable-закачка JDK/Maven по требованию
api.py          JSON CLI-режим и HTTP API-сервер
gui_common.py   сводка по jar (`jar_summary()`, используется Electron-
                клиентом через `--jar-summary`), путь к папке настроек
                (`get_app_data_dir()`, также нужен toolinstaller.py) - имя
                исторически осталось от старого GUI (см. HANDOFF_4), но
                сам файл больше не про GUI-темы: gui.py/gui_raw.py/
                gui_neon.py/gui_md3.py физически удалены из репозитория
run.bat/run.sh  точки входа
icon.ico/icon.png   иконка (сгенерирована через PIL, не внешний файл)
```

GUI-клиент (Electron + React, отдельно от движка выше) — см. раздел
[GUI](#gui-windowsmacoslinux):
```
electron/main.ts      главный процесс: IPC-хендлеры, спавн движка, настройки
electron/preload.ts    мост в рендерер (window.nano.*)
electron/updater.ts    автообновление (движок и клиент отдельно)
src/App.tsx            весь UI одним компонентом
src/styles.css          стили
```

**Ключевой принцип, который нельзя нарушать:** если декомпилятор не уверен
на 100% в конкретном методе — он обязан откатиться на честный
дизассемблированный листинг байткода (`DecompileAbort` в `engine.py`)
вместо того, чтобы напечатать код, который может быть неправильным.

## Тестирование / регрессия

В `test_jars/` лежат тестовые jar'а разной сложности:
- `EryBuyer-v1.jar` — шейдит sqlite-jdbc, интерфейсы, enum, synchronized.
  Самый прогоняемый jar в истории проекта — **97.8%** методов полностью
  восстановлены (было 91.7% на начало v1.4 — см. `HANDOFF_8`…`HANDOFF_15`
  за подробностями каждого фикса).
- `DeathUtils-1_0.jar` — шейдит sqlite-jdbc **релоцированный** (проверяет
  детект релокаций).
- `GlowClans-0_1-fork.jar` — реальный лог `mvn clean package` нашёл 6+
  реальных багов движка в своё время. Есть `@NotNull` (JetBrains).

Прогон регрессии:
```bash
for j in test_jars/*.jar; do
    python3 main.py "$j" "/tmp/out_$(basename "$j" .jar)"
done
```
`DeathUtils`/`GlowClans` не переприверялись в сессии v1.4 (в песочнице той
сессии их не было — вместо них использовался более широкий набор из 11
сторонних плагинов пользователя, не входящих в `test_jars/`) — их числа в
этом README могут быть устаревшими относительно текущего движка. Перед
релизом стоит прогнать их заново и обновить эту строку.

Общее правило: заметная просадка на любом jar'е после правки — сигнал,
что новый фикс/проверка ложно срабатывает. Сначала смотри
`stats.fallback_reasons` в `README_RU.txt`/JSON-выводе (какая именно
причина отката выросла), не гадай и не откатывай фикс вслепую — см.
историю в `HANDOFF_2_FIXES_HISTORY.md` (там разбор именно такого случая)

## Сборка в .exe (Windows)

Два раздельных артефакта (см. `.github/workflows/build-and-release.yml` —
собираются автоматически при пуше в `main`, версия берётся из
`package.json`, см. `HANDOFF_16_VERSION_SINGLE_SOURCE.md`):

**Движок (headless CLI/API, без GUI вообще)** — `NanoDecompilerCLI.exe`,
тот же самый `main.py`, упакованный в один файл:
```
pyinstaller --onefile --name NanoDecompilerCLI main.py
```
(без `--windowed` — это консольный exe, GUI-клиент вызывает его как
дочерний процесс с аргументами, см. `electron/main.ts::engineInvocation()`).

**GUI-клиент (Electron + React)** — `NanoDecompiler-Client-Setup.exe`:
```
npm run dist
```
(`electron-builder`, конфигурация — `package.json`; версия инсталлятора и
`app.getVersion()` внутри собранного приложения читаются из
`package.json` нативно).

Ни то, ни другое не кросс-компилируется — собирать нужно реально на

`windows-latest`-раннером, пуш из Termux, скачать готовые файлы из
Releases/Artifacts — именно так и настроен CI).

## Известные ограничения

- **`synchronized(){}`**: настоящая свёртка `monitorenter`/`monitorexit` не
  реализована — если найден несвёрнутый монитор, честно откатывается на
  байткод вместо потери семантики блокировки.
- **`try`/`finally`**: восстанавливается как несколько `catch(Throwable)` с
  дублированием кода вместо одного `finally {}` — семантически верно,
  компилируется, но не идиоматично для чтения.
- **Переиспользование JVM local-слота под разные типы** в
  try-with-resources suppressed-exception ветках (`addSuppressed`) — может
  дать код, который не компилируется (несовпадение типов на одном
  «логическом» имени переменной). Диагностировано, не починено — см.
  `HANDOFF_12_VAR7_SLOT_REUSE_INVESTIGATION.md`. Нужен pattern-matcher на
  форму try-with-resources целиком, а не патч поверх текущего именования
  catch-переменных (точечная попытка исправить это заменила ошибку
  компиляции на молчаливый неверный рантайм — откачена).
- Отдельные крупные методы со стримами/лямбдами (`invokedynamic`) могут
  падать на "несогласованная глубина пересечения стека" даже после фикса
  из `HANDOFF_13`/`HANDOFF_15` — не разбирались глубоко (см.
  `DeluxeMenuConstructor.loadMenu()` в `HANDOFF_15`).
- **Electron-клиент**: правки в `src/App.tsx`/`electron/*.ts` (включая
  экран настроек, v1.4.2) проверялись только синтаксически (баланс
  скобок/типов вручную) — в песочнице нет сети для `npm install`, поэтому
  ни `tsc`, ни реальная сборка/визуальная проверка на экране не
  выполнялись. Стоит собрать и открыть один раз перед релизом.

**Дженерики полей/методов/класса** (атрибут `Signature`) реализованы
полностью, включая вложенные generic-типы и wildcard'ы — это раньше было
известным ограничением, с v1.х больше не актуально (см.
`HANDOFF_7_SESSION_AND_TWR_BUG.md`, аддендумы 4 и 6).

## Диагностика проблем

**Клиент пишет «Декомпиляция уже запущена» и ничего не происходит:**
`electron/main.ts` держит только ОДИН запущенный процесс движка за раз
(`runningProc`) — если предыдущий запуск завис (напр. дочерний
`python3`/`NanoDecompilerCLI.exe` не отвечает), кнопка «ОСТАНОВИТЬ»
должна его убить (`run:cancel` → `proc.kill()`). Если и это не помогает —
перезапусти клиент целиком; зависший процесс движка сам завершится вместе
с родительским Electron-процессом.

**Тумблеры в настройках не сохраняются между запусками:**
Настройки лежат в `<userData>/settings.json` (см. `electron/main.ts::settingsPath()`
— на Windows это `%APPDATA%\NanoDecompiler\settings.json`). Если файл
повреждён или содержит не-булево значение по какому-то из двух ключей —
`loadSettings()` тихо подставляет дефолт ИМЕННО для этого ключа (не роняет
остальные настройки) - проверь сам файл, если тумблер стабильно не
держится.

**«На Windows всегда пишет, что Maven/Java отсутствует», хотя точно
установлены:**
Частая причина — `PATH` обновился в реестре установщиком, но текущий
процесс (особенно если приложение запущено двойным кликом через
explorer.exe) унаследовал старое окружение и не видит изменения до
перезахода в систему/перезагрузки. Проверка теперь дополнительно читает
свежий `PATH` из реестра и типичные пути установки — если находит именно
так, явно пишет «найден(а) вне PATH» + путь + подсказку про перезагрузку.
Если и это не помогает — попробуй `python3 main.py --install-tools`,
это ставит portable-копию рядом, независимо от системного `PATH`.

**Любая другая непонятная просадка после правки движка** — сначала смотри
`stats.fallback_reasons` в `README_RU.txt`/JSON-выводе (какая именно
причина отката выросла), не гадай и не откатывай фикс вслепую (см. историю
в `HANDOFF_2_FIXES_HISTORY.md` — там разбор именно такого случая).
