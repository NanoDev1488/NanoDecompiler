# HANDOFF 6: "деобфусцированный код нечитаем" - разбивка на подзадачи

Продолжение HANDOFF_1-5. Пользователь на прямой вопрос "что именно плохо
выглядит" ответил "всё сразу": (1) control-flow flattening (спагетти
if/switch/goto), (2) зашифрованные строки (decrypt(...) вызовы), (3)
мусорный код / opaque predicates. Это ТРИ РАЗНЫЕ фичи с очень разным
уровнем риска - см. по каждой ниже. Ключевой принцип проекта (HANDOFF_1,
"НЕ НАРУШАТЬ") - лучше честно откатиться, чем напечатать код, который МОЖЕТ
быть неверным - применяется и здесь: не стал делать все три одним рывком
без возможности проверить на реальном обфусцированном jar'е (в песочнице
нет javac, нет сети для JDK/обфускаторов - см. ниже).

## 1. ГОТОВО: opaque predicates / мёртвые ветки (constfold.py, новый файл)

`try_eval_const(expr)` - строго формальная (JLS §15.28 constant folding, не
эвристика) свёртка выражений, целиком состоящих из литеральных констант +
чистых арифметических/логических/битовых операций, БЕЗ единой переменной/
поля/вызова. Если хоть один узел дерева не константа - возвращает `None`,
ничего не трогаем (тот же принцип, что `DecompileAbort`).

`fold_dead_branches()` подключена в `structure.py::simplify_stmts` - если
`if`-условие сворачивается в `True`/`False`, ветка убирается, вторая
инлайнится на её место. Гоняется до стабилизации в рамках одного уровня
списка операторов (обычно 1 проход).

Статистика (`constfold.get_dead_branches_removed()`, сбрасывается per-jar
через `reset_stats()` в начале `process_jar_with_stats` - ВАЖНО для
`--api-server` режима, иначе счётчик тёк бы между jar'ами одного процесса)
- новая секция в README_RU.txt "СВЁРТКА OPAQUE PREDICATES", печатается
только если что-то реально убрано.

ПРОВЕРЕНО: 10 юнит-тестов на `try_eval_const` (включая переполнение int при
`2147483647 * 2` - маскирование по разрядности, а не голый Python-инт;
деление на 0 и "условие с переменной" корректно возвращают `None`, то есть
НЕ сворачиваются) + `fold_dead_branches` на синтетическом дереве. Полная
регрессия на `EryBuyer-v1.jar` - 0 отличий (этот jar не содержит opaque
predicates, регрессия подтверждает отсутствие ложных срабатываний на
чистом коде).

НЕ ПРОВЕРЕНО (честно): нет живого обфусцированного jar'а под рукой (в
песочнице нет `javac` - только `java` runtime без JDK, и нет сети, чтобы
поставить JDK или воспользоваться реальным обфускатором для синтетического
теста). Логика проверена только юнитами + не сломала реальный jar. Как
только появится реальный обфусцированный jar с opaque predicates (или
доступ к JDK в песочнице) - прогнать и свериться визуально с ожиданием.

НЕ СДЕЛАНО В ЭТОМ ПРОХОДЕ (сознательно, риск/выгода не в пользу): свёртка
`while(false){}` (тело гарантированно не выполняется ни разу) и инлайнинг
`do{...}while(false)` (тело выполняется РОВНО один раз) - технически тоже
безопасны сами по себе, но требуют доп. проверки на `break`/`continue`
внутри тела (может ссылаться на убираемый цикл как на target) - не стал
рисковать без времени на аккуратную проверку, оставил как есть.

## 2. НЕ СДЕЛАНО: зашифрованные строки (`decrypt(...)` вызовы)

Идея (безопасный вариант, тот же принцип "не гадать"): если вызываемый
метод-расшифровщик ЦЕЛИКОМ находится внутри разбираемого jar'а, ЧИСТЫЙ (не
трогает поля/статики/сеть/файлы - только аргументы + константы + базовая
арифметика/строковые операции), и ВСЕ его аргументы в точке вызова -
константы (LDC) - можно реально ВЫПОЛНИТЬ этот метод (написать мини-
интерпретатор JVM-байткода метода на Python, как частный случай
"вычисления с известными входами", концептуально то же самое, что
`constfold.py` делает для арифметики, только на уровне целого метода, а не
одного выражения) и подставить РЕЗУЛЬТАТ вместо вызова, с явным
комментарием `/* deobfuscated string, verified by execution */`.

НЕ НАЧАТО. Это отдельный, довольно большой кусок работы (мини-интерпретатор
байткода метода, а не просто выражения - нужно уметь исполнять циклы,
локальные переменные, StringBuilder и т.п. внутри самого decrypt-метода) -
не стал делать наспех в этом же проходе поверх opaque predicates. Если
браться - логично переиспользовать `stackvm.py` (там уже есть символическое
исполнение) в режиме "все входы известны -> материализовать в конкретное
значение", а не писать интерпретатор с нуля.

## 3. НЕ СДЕЛАНО: control-flow flattening (dispatcher `while+switch`)

Это САМАЯ рискованная из трёх фич - в отличие от 1 и 2 (локальные,
формально проверяемые преобразования одного выражения/вызова), unflattening
меняет ТОПОЛОГИЮ CFG целого метода. Общий (надёжный на произвольном
обфускаторе) алгоритм восстановления реального порядка блоков из
`while(true){ switch(state){ case 1: ...; state=X; break; ... } }` -
исследовательская задача сама по себе (state variable не всегда простой
int-счётчик; бывают несколько state-переменных, откуда обфускатор
"мешает" порядок; не бывает 100% общего решения без риска дать НЕВЕРНЫЙ,
но похожий на правильный код - то есть ровно то, что `DecompileAbort`
призван не допускать).

Реалистичный безопасный первый шаг (не начат): не пытаться восстановить
топологию, а хотя бы РАСПОЗНАТЬ паттерн dispatcher-цикла и явно ПОМЕТИТЬ
такой метод в выводе (комментарий `/* похоже на flattened control flow
(dispatcher-цикл на переменной X) - топология не восстановлена, читайте
как есть */`) - честно, не обманывает читателя, что это "нормальный" код,
без риска сломать корректность. Полноценное восстановление - отдельная
большая сессия, нужен как минимум один реальный образец (ProGuard/Allatori
с flattening в паре тестовых jar) для итеративной проверки - без него
любая попытка будет гаданием вслепую, что противоречит ключевому принципу
проекта.

## Что стоит сделать дальше (порядок по соотношению риск/польза)

1. Если появится сеть в песочнице или реальный обфусцированный jar от
   пользователя - в первую очередь визуально проверить п.1 (opaque
   predicates) на реальных данных, не гадать по юнитам.
2. Детект (без восстановления) `while(true)+switch` dispatcher-паттерна -
   дешёвая, честная, безопасная польза (см. п.3 выше) - хорошая следующая
   маленькая задача перед тем, как браться за полноценный unflattening.
3. Строковый дешифратор (п.2) - самая полезная из оставшихся для конечного
   пользователя (маскирует конкретные данные типа URL/токенов), но требует
   заметно больше кода (мини-исполнение метода, не выражения).
4. Полноценный control-flow unflattening - только после (1)+(2)+(3) и
   только если найдётся хотя бы 2-3 реальных jar с этим паттерном для
   регрессии - см. философию HANDOFF_1/2 про "не оптимизировать процент
   успеха в ущерб честности".
