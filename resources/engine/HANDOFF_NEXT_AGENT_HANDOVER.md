# NanoDecompiler — состояние проекта (актуально на v1.6.3 BETA)

Этот файл заменяет всю предыдущую историю хэндофов (HANDOFF_1..54) -
она перенесена в `archive/` этой же папки, не удалена, но не нужна для
продолжения работы. Если что-то из текущего описания противоречит файлу
в `archive/` - верить ЭТОМУ файлу, он новее.

## Что это за проект

Декомпилятор Java-байткода (.class/.jar → .java) для серверных плагинов
Minecraft. Движок на C++17 (`resources/engine_cpp/`), GUI на
Electron+React+TypeScript+Tailwind (`src/`, `electron/`).

Движок и CLI/API - ОДИН бинарник (`cli_main.cpp`): обычный режим,
`--json-output`, `--api-server` (HTTP), `--jar-summary`, `--version`.
Отдельного `NanoDecompilerAPI` не существует - если увидите упоминание,
это устаревший текст.

## Архитектура GUI (важно - GUI был ПОЛНОСТЬЮ заменён в этой сессии)

Старый GUI (react-codemirror based mini-IDE) заменён на дизайн от
GUI-разработчика проекта (t.me/dyrachuna) - компоненты в `src/components/`:
`AppHeader`, `Sidebar`, `FileTree`, `CodeView`, `Workspace`, `Terminal`,
`StatusBar`, `Titlebar`, `SettingsModal`, `UpdateModal`, `CommandPalette`,
`Toasts`. Вся связь с реальным движком - через `window.nano.*`
(контракт в `electron/preload.ts` + `src/global.d.ts`), реализация
хендлеров - `electron/main.ts`. Состояние - `src/state/engine.tsx`
(единственный источник правды, React Context, никакого Redux/Zustand).

Раньше этот же новый GUI был ПОЛНОСТЬЮ на моках (`fixtures.ts`,
таймеры-симуляции) - теперь всё реально подключено к движку. Файл
`fixtures.ts` удалён, если увидите импорт из него - это баг.

## Что сделано (эта сессия, кратко - без пересказа истории до неё)

- Реальный баг в `hoist_escaping_locals`/`collect_shallow_referenced_names`
  (engine.cpp) - переменные внутри if/while/for/try не поднимались наружу
  корректно. Исправлено, регрессия подтверждена.
- META-INF/MANIFEST.MF и META-INF/maven/* больше не копируются как
  ресурсы в вывод (process_jar.cpp) - раньше засоряли структуру и
  задваивались бы при mvn package.
- H2 и OrmLite (даже релоцированные под произвольный shade-префикс)
  теперь фильтруются как известные библиотеки (lib_filter.cpp,
  pom_builder.cpp) - раньше OrmLite не фильтровалась, и один из её
  методов (`writeConfig`, длинная плоская цепочка if без else) вешал
  Structurer на много минут. См. "Открытую проблему" ниже - сама причина
  зависания НЕ исправлена, только обойдена фильтрацией.
- Windows-баги: `shell_quote()` не экранировал `"` (toolinstaller.cpp),
  CMakeLists.txt не линковал `ws2_32` (Winsock для --api-server),
  `<cstdint>` не был явно инклюднут в 29 файлах (транзитивно работало на
  Linux/GCC, падало на MinGW).
- electron/main.ts: `flushLines` склеивал stdout/stderr в один буфер,
  `run:cancel` не убивал дочерние процессы движка (curl и т.п.),
  `dialog:selectJar` не поддерживал мультивыбор.
- **Апдейтер** (`electron/updater.ts`): версия движка бралась только из
  файла-маркера, который никогда не создавался на свежей установке -
  апдейтер вечно врал "доступно обновление". Теперь спрашивает бинарник
  напрямую (`--version`). Ассеты релиза переименованы под новую CI-схему
  (см. ниже) - `ENGINE_ASSET_NAME` обновлён.
- **Детекция платформы** (новый модуль `platform_detect.hpp/cpp`):
  Bukkit/Spigot (`plugin.yml`), Paper (`paper-plugin.yml`), Velocity
  (`velocity-plugin.json`), BungeeCord (`bungee.yml`). Fabric/Forge/
  NeoForge МОДЫ распознаются отдельно и декомпиляция для них
  ПРЕРЫВАЕТСЯ сразу (`status:"mod_rejected"` в JSON, понятный текст
  пользователю) - моды временно не декомпилируются по прямому решению
  пользователя, это не баг, а осознанное ограничение.
- Хардкод-версии по всему GUI (`"2.4.1"`, `"GUI v2.1.0"`, выдуманный git-
  хэш `"build a3f9c2"`) заменены на настоящие через `--version`/
  `app.getVersion()`. `java -version`/`mvn -version` теперь реально
  проверяются (`env:check` в main.ts), а не фейковый UI-тумблер.
- Иконка приложения: старая (клипарт-баночка+звёздочка, потом версия со
  скобками) заменена. Пользователь выбрал `icon-b-terminal` (курсор
  `>_`) как основную, `icon-e-layers` как второй вариант в GUI-пикере
  (Settings → Основные → "Иконка приложения"). ВАЖНО: рантайм-переключение
  меняет только лого в шапке (`Titlebar.tsx`) и иконку окна
  (`mainWindow.setIcon()`, работает на Windows/Linux, НЕ на macOS) - саму
  иконку `.exe`/`.app` в рантайме поменять нельзя, это ограничение ОС,
  зашивается при сборке (`resources/engine/icon.ico`/`icon.png`).
- CI (`build-and-release.yml`): было 3 клиента + 1 `build-api`
  (Windows-only). Стало 3 клиента + 3 `build-clapi-*` (Windows/Linux/
  macOS) - CLI и API остаются ОДНИМ бинарником, но теперь публикуются
  под всеми тремя платформами с именем `NanoDecompilerClApi-<os>`.
  `publish-release` требует успеха всех 6 job'ов разом.
- Регрессия прогнана на полном корпусе 66 реальных jar (из
  `plugins-for-test.zip` пользователя) - 0 падений, 0 зависаний. 8 файлов
  дают 100% декомпиляции, остальные в диапазоне 76-99% (контролируемые
  fallback'и, не баги).

## Открытая проблема (НЕ исправлена, важно знать)

`Structurer::build_if_inner`/`find_forward_merge` (structure.cpp) реально
уходит в многоминутное зависание на методах с длинной ПОСЛЕДОВАТЕЛЬНОЙ
(не вложенной) цепочкой `if (cond) { ...; }` без `else` - воспроизведено
на `DatabaseFieldConfigLoader.writeConfig` из OrmLite (83 блока, 600
инструкций). Причина ПОКА НЕ найдена - есть гипотеза, что `ipdom_`
(immediate post-dominator) не находит merge для этих блоков и каждый `if`
проваливается в `find_forward_merge` без общей мемоизации между соседними
`if` на одном уровне. Сейчас эта проблема обойдена фильтрацией известных
библиотек (H2/OrmLite), а не исправлена в самом алгоритме - если такой же
паттерн (много последовательных if без else) встретится в коде САМОГО
плагина (не библиотеки), зависание всё ещё возможно. Полноценный фикс
требует отдельной аккуратной сессии в structure.cpp - НЕ делать наспех
(есть guard `if_chain_depth_ > 800` для вложенных цепочек, но он не
защищает от этого случая - последовательные, не вложенные if).

## Реально оставшиеся задачи (по приоритету, обсуждено с пользователем)

1. **goto / недостижимые-но-живые блоки** (structure.cpp) - САМАЯ крупная
   категория fallback'а (~254 случая на момент последнего замера,
   HANDOFF_49 в архиве). Требует node-splitting или аналогичного алгоритма
   для CFG. Рискованная задача, делать аккуратно, с полной регрессией
   после. См. также "Открытую проблему" выше - возможно, тот же класс
   алгоритмических проблем.
2. Параметры record-конструктора не переименовываются под имена
   компонентов (косметика, низкий приоритет).
3. `build_pom` для Velocity/Bungee без встроенного оригинального pom.xml
   в jar использует имя файла jar как artifactId, а не
   `platform.name` (который уже корректно парсится, см.
   `platform_detect.cpp`) - минорный, не функциональный пробел.

## Жёсткие уроки этой сессии (чтобы не наступать повторно)

- **Pillow ICO**: `img.save(path, format='ICO', sizes=[...], append_images=[...])`
  может НЕ включить корректный кадр нужного размера (напр. 256x256) -
  правильно: один мастер-файл максимального разрешения, `sizes=[...]`
  БЕЗ `append_images`, Pillow сам даунскейлит. Проверять через
  `Image.open(path).ico.sizes()`.
- **package.json version**: НИКОГДА не добавлять суффикс типа `-beta` -
  `resolve-version` job в CI парсит его как строгий semver
  (`cut -d. -f3`), суффикс ломает сравнение PATCH. "BETA" в тексте -
  только в `version.hpp` (строка движка), не в самой версии тега/пакета.
- **`<cstdint>`**: транзитивно работает на Linux/GCC через другие
  заголовки, падает на MinGW/Windows с "int64_t was not declared" -
  инклюдить явно во всех файлах, использующих `int64_t`/`uint32_t` и т.п.
- **MinGW + Winsock**: заголовки (`winsock2.h`) не гарантируют линковку -
  `target_link_libraries(... ws2_32)` нужен явно в CMakeLists.txt.
- **`.gitignore`**: если игнорируете `NanoDecompilerCLI.exe`, не забудьте
  и голый `NanoDecompilerCLI` (Linux/macOS, без расширения) - легко
  забыть один из двух.
- Пользователь **всегда собирает через GitHub Actions**, не локально -
  не класть скомпилированные бинарники в архивы для него, только
  исходник. Компилировать локально (в песочнице агента) - только для
  собственной regression-проверки перед отдачей.
- При батчевой обработке файлов через bash-цикл с перемещением файлов
  (`mv ... regress_done_100/`) - статичный список путей (`jarlist.txt`)
  устаревает после первого же перемещения. Либо перегенерировать список
  каждый раз (`ls ... > jarlist.txt`), либо проверять `[ -f "$f" ]` перед
  обработкой.

## Общие принципы (соблюдались всеми сессиями, продолжайте)

- Каждый найденный баг - подтверждать реальным воспроизведением
  (компиляция/прогон), не полагаться на "выглядит подозрительно".
- Регрессия на реальных jar после КАЖДОГО значимого изменения движка -
  `test_jars/large_legit/BukkitOfUtils-1_19_0.jar` для быстрой проверки,
  полный корпус `plugins-for-test.zip` (66 файлов пользователя) - для
  финальной проверки перед отдачей.
- Не чинить "на всякий случай" - только реально найденные, воспроизведённые
  проблемы.
- Отдавать пользователю ВЕСЬ проект архивом целиком, не отдельные файлы -
  явная его инструкция.
