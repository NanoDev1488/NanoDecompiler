### Ключевое архитектурное решение: `_mutate_into` не переносится буквально

Оригинал в `_simplify_while_true` меняет `__class__` объекта прямо на
месте (`while_stmt.__class__ = DoWhileStmt`) - в C++ у объекта нельзя
поменять динамический тип. Вместо этого `simplify_while_true`/
`simplify_stmt` в порту **возвращают** `StmtPtr` (тот же указатель, если
преобразование не произошло, либо НОВЫЙ узел `DoWhileStmt`/`ForStmt`,
если произошло) - и `simplify_stmts` строит НОВЫЙ вектор из возвращённых
значений, а не полагается на мутацию в изначальном списке. Это
безопасно, т.к. в этом AST каждый `Stmt`-узел имеет РОВНО одного
родителя (не DAG с расшаренными под-деревьями на уровне `Stmt` - в
отличие от `Expr`, где `_PendingNew`/dup-копии НАМЕРЕННО расшарены -
см. HANDOFF_29/36).

### Три РАЗНЫХ generic-обходчика AST - намеренно не унифицированы

`_rename_local`, `_contains_local_ref`, `_substitute_temp` в оригинале -
похожие, но **не идентичные** обходы дерева (разные наборы проверяемых
атрибутов). Например, `_rename_local` НЕ заходит в `ForStmt.update`
(гейт `hasattr(v,"prec")` в Python отсекает Stmt-объекты), НЕ заходит в
`BlockStmt.stmts` (в generic-списке атрибутов есть только `"body"`, а не
`"stmts"`) и НЕ заходит в `TryStmt.finally_body` (не в списке атрибутов
для этой функции). А вот `_contains_local_ref` использует ДРУГОЙ,
чуть более широкий список - включает `finally_body`, и не имеет
Expr-only гейта, поэтому реально доходит до `ForStmt.update` (через
вложенный `ExprStmtNode.expr`). Портированы как ТРИ раздельные функции
с точно теми же (разными!) ограничениями каждая - не как одна общая
"reflection"-функция, чтобы не потерять эти умолчания.

### Регрессия

Полноценный end-to-end тест structure.py требует посева
exception-handler блоков (`Local(CAUGHT_SENTINEL,"Throwable")` на
entry_stack) - в оригинале это делает ещё не перенесённый `engine.py`.
Для ЭТОЙ сверки реализован МИНИМАЛЬНЫЙ эквивалент этого одного шага
(тот же посев, без остальной логики `engine.py` - меж-блочного
проброса стека и т.п.) - и на C++, и на Python-стороне ОДИНАКОВО,
чтобы сверка была честной проверкой именно `structure.py`.

`dump_structure` (C++) / `dump_structure_ref.py` (Python) - прогнано на
всех 4075 классах из всех 13 джарников пользователя:

- **4067/4067 сопоставимых классов - 0 расхождений** (после исправления
  одного форматирования - см. ниже).
- **8 классов** - оригинальный Python падает с `RecursionError:
  maximum recursion depth exceeded` (глубоко вложенная цепочка `if/elif`
  - типичный паттерн для скомпилированных больших `switch`-подобных
    конструкций типа фильтра нецензурных слов - `ProfanityEngine.class`
    и аналогичные). Это ограничение САМОГО Python-интерпретатора
  (рекурсивный `region()`/`_build_if` упирается в лимит стека
  CPython ~1000 кадров) - НЕ баг порта. C++-версия использует обычный
  стек ОС (по умолчанию куда больше) и успешно структурирует эти же
  классы без проблем - в этом смысле порт объективно МЕНЕЕ хрупкий на
  таких данных, чем оригинал (не "исправление баланса" specifically,
  а естественное следствие другой модели рекурсии).
- **4 класса** - автосгенерированные `com.google.protobuf.
  DescriptorProtos$*$Builder` классы (огромные методы) - ОБЕ реализации
  не укладываются в 90 секунд ОДИНАКОВО (`timeout` на обеих сторонах) -
  не расхождение, общая характеристика производительности на
  экстремальном (не характерном для обычных Minecraft-плагинов) входе.
  Не расследовалось дальше в рамках этой сессии - для реальных плагинов
  пользователя такого рода классы не встречаются.

### Найденный и исправленный баг ПОРТА (не в оригинале)

Сообщение об ошибке в `check_full_coverage` форматировало список
недостижимых блоков как `{104, 156}` (фигурные скобки, "по-питоновски
для set") вместо `[104, 156]` (квадратные скобки - Python
`f"{sorted(missing)}"` форматирует ИМЕННО `list`, не `set`, т.к.
`sorted()` всегда возвращает список). Мелочь, но ловится побайтовой
сверкой текста ошибки - поймано и исправлено сразу на первом же
прогоне маленьких джарников.
