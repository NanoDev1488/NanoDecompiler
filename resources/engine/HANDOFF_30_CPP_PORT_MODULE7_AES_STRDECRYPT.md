# HANDOFF_30: Модуль 7 - aes128.py + str_decrypt.py -> C++, сверено
# (NIST-вектор, hashlib, и сквозной сценарий шифрование/расшифровка)

## aes128.py -> aes128.hpp/cpp

Перенесено полностью (только расшифровка, как и в оригинале - шифрование
не нужно и не реализовано): `_key_expansion_128`, `decrypt_block`
(InvShiftRows/InvSubBytes/AddRoundKey/InvMixColumns в обратном порядке),
`aes128_ecb_decrypt`, `unpad_pkcs7`. Сверено с официальным тестовым
вектором **NIST FIPS-197 Appendix C.1** (тот же вектор, что использует
сам `aes128.py` в своём `if __name__ == "__main__"` блоке) - совпадает.

## Новые вспомогательные модули (без прямого Python-аналога в движке)

`str_decrypt.py` использует `hashlib.sha256` и `base64.b64decode` из
стандартной библиотеки Python - в C++ такого "бесплатно" нет, и по духу
проекта (принципиально без внешних зависимостей - см. комментарии в
`aes128.py`) эти два примитива тоже написаны с нуля:

- **`sha256.hpp/cpp`** - стандартный SHA-256 (FIPS-180-4). Сверено с
  `hashlib.sha256` побайтно на пустой строке, `"abc"` и на seed-байтах
  `build_key` - совпадает.
- **`base64.hpp/cpp`** - строгий base64-декодер, аналог
  `base64.b64decode(s, validate=True)`. Здесь обнаружилась интересная
  деталь: **реальное поведение CPython - НЕ простой "regex + длина
  кратна 4"**, как можно было бы предположить по докстрингу модуля
  `base64` - это внутренний C-код `binascii.a2b_base64(s,
  strict_mode=True)` со своей логикой допустимого паддинга. Пришлось
  разобраться дифференциальным тестированием (~1259 случайных и
  специально подобранных строк - валидные/невалидные длины, битые
  символы, `=` в середине, недостаточный/избыточный паддинг, паддинг без
  данных) против самого `base64.b64decode` в Python, пока не сошлось
  **0 расхождений**. Итоговое правило (см. комментарий в коде): при
  `data_len % 4 == 0` (данные без учёта хвостовых `=`) - любое
  количество хвостовых `=` допустимо и игнорируется; при `% 4 in {2,3}`
  - количество `=` должно РОВНО совпасть с недостающим; `% 4 == 1` -
  всегда ошибка; данные отсутствуют, но `=` есть - тоже ошибка.

## str_decrypt.py -> str_decrypt.hpp/cpp

Перенесено полностью: `has_marker`, `build_key`, `decrypt_string`,
`find_decryptor_in_class`, `decrypt_method_name`. Добавлена своя
UTF-8-валидация (Python вызывает `.decode("utf-8")`, что бросает
исключение на некорректных байтах - поймано широким `except`, значит
расшифровка молча отклоняется; C++ версия делает то же самое явной
проверкой валидности UTF-8 перед возвратом результата).

Модульное состояние `ACTIVE`/`DECRYPTED_COUNT` (глобальный "текущий
расшифровщик для этого jar", читается из `stackvm.py`) - НЕ перенесено
в этом модуле: у него пока нет потребителя (`stackvm.py`/`main.py` не
портированы), переносить raw-состояние без кода, который его
использует, преждевременно - будет добавлено вместе со `stackvm.py`.

### Регрессия

1. `aes128`: официальный NIST-вектor - совпадает.
2. `sha256`: сверка с `hashlib.sha256` - совпадает.
3. `base64`: дифференциальное тестирование с `base64.b64decode(...,
   validate=True)` - 1259 случаев, 0 расхождений (после исправления
   найденной неточности в понимании правил паддинга).
4. **Сквозной сценарий**: настоящее AES-128-ECB+PKCS7 шифрование через
   `cryptography` (сторонняя библиотека - используется ТОЛЬКО для
   генерации тестовых данных, не часть самого движка) на разнообразных
   строках (ASCII/кириллица/китайские иероглифы/спецсимволы/пустая
   строка/200 символов) -> расшифровка через C++ порт - все совпали с
   исходником. Плюс **прямая сверка с оригинальным `str_decrypt.py`**
   (`build_key`+`decrypt_string`) на 50 случайных (h, l, строка) - 0
   расхождений.

## ЧТО ЕЩЁ НУЖНО СОЗДАТЬ (для полного v2.0)

По убыванию приоритета / порядку зависимостей:

1. **`stackvm.py` (1096 строк)** - САМЫЙ большой и сложный оставшийся
   модуль: символическая интерпретация стека JVM поверх CFG, строит
   AST (`ast_nodes`, уже перенесён) из инструкций. Обрабатывает
   invokedynamic/лямбды/string-concat (тесно связан с уже перенесённым
   `str_decrypt.py`), dup-семейство, unboxing, MethodCtx (имена
   локальных переменных, temp-переменные). Требует отдельной сессии:
   сначала дочитать файл целиком (был открыт частично, участок
   212-885 строк не дочитан), потом перенос, потом содержательная
   регрессия на реальных jar.
2. **`structure.py` (1119 строк)** - структуризация CFG обратно в
   if/while/for/switch/try (вместо голых goto). Зависит от `cfg`
   (готов) и `ast_nodes`/`stackvm` (частично/не готовы).
3. **`emit.py` (232 строки)** - печать AST (`ast_nodes`) в текст Java.
   Нужен, чтобы вообще увидеть результат работы `stackvm`+`structure`.
4. **`verify.py` (254 строки)** - проверки/самоконтроль результата
   декомпиляции.
5. **`engine.py` (1322 строки)** - оркестрация: класс -> байткод ->
   CFG -> stackvm -> structure -> emit, с откатом на честный
   дизассемблированный листинг при `DecompileAbort`.
6. **`main.py` (1654 строки)** - CLI/точка входа, обработка jar
   целиком, интеграция с `str_decrypt`/`malware_scan`/`toolinstaller`
   и т.д.
7. Более мелкие модули, ещё не тронутые: `malware_scan.py` (376),
   `legitimacy_check.py` (257), `pom_builder.py` (388),
   `toolinstaller.py` (449), `api.py` (219), `gui_common.py` (195),
   `emit.py` (уже в п.3), `catchclean` (упоминался в HANDOFF_25 как
   отдельный от `disassembler` - надо перепроверить, существует ли
   отдельным файлом или это часть `main.py`).
8. Пункты 1-3 из HANDOFF_23 (мини-язык для сайтов легитимности,
   `training.py`, доп. настройки v2) - изначальный план, отдельный от
   переноса движка, статус не менялся, не начаты.

Порядок 1-6 - это фактически последовательная цепочка зависимостей до
"движок реально что-то декомпилирует" - `stackvm.py` (п.1) технически
самый логичный следующий шаг (без него `structure`/`emit`/`engine`
нечего обрабатывать), но самый трудоёмкий - если предпочтительнее
сначала более короткие независимые модули (`verify.py`,
`malware_scan.py`, `legitimacy_check.py`, `pom_builder.py`,
`toolinstaller.py`, `api.py`, `gui_common.py` - все не зависят от
`stackvm`/`structure`/`emit`), это тоже валидный порядок - можно
параллельно продвигать, пока `stackvm.py` ждёт отдельной сессии.
