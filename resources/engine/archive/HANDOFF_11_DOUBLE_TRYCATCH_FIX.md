# HANDOFF_11: Двойной try/catch с одинаковыми типами исключений - НАСТОЯЩАЯ
# причина найдена и починена (это была НЕ вложенность вообще)

Продолжение HANDOFF_10 в той же сессии. Закрывает последний известный
пункт "что дальше" - `SkullUtils.applyPlayerProfileSkullReflect`.

## Диагностика: реальный байткод, не гадание

Вытащил exception-table метода напрямую из .class внутри jar
(`classfile.ClassFile` + чтение `m.exceptions`):

    start=0  end=32  handler=121 type=ClassNotFoundException
    start=33 end=120 handler=121 type=ClassNotFoundException
    start=0  end=32  handler=124 type=MalformedURLException
    start=33 end=120 handler=124 type=MalformedURLException
    start=0  end=32  handler=140 type=ReflectiveOperationException
    start=33 end=120 handler=140 type=ReflectiveOperationException

Т.е. КАЖДЫЙ из 3 типов исключений встречается ДВАЖДЫ, с диапазонами
(0,32) и (33,120), и ОДИНАКОВЫМ handler_pc для обеих половин каждого
типа. Это НЕ два вложенных try - это ОДИН логический try/catch, чью
защищённую область javac разрезал на два смежных куска в exception-
table. Дизассемблировал инструкцию на границе (pc=32): `ireturn` - голый
`return`, который САМ ПО СЕБЕ бросить исключение не может, поэтому
компилятор законно исключил именно эту ОДНУ инструкцию из защищённого
диапазона, хотя семантически `return false;` находится ВНУТРИ того же
try-блока в исходнике.

Старый `_prepare_try` группировал exceptions СТРОГО по (start_pc,
end_pc) - две половины с разными диапазонами превращались в ДВА разных
try/catch при построении, с задвоенными catch-блоками (`ClassNotFound`/
`MalformedURL`/`ReflectiveOperation` - каждый дважды) и невалидными
именами catch-переменных вне области видимости (`e1` из внутреннего catch
использовался во внешнем).

## Фикс: `_merge_split_exception_ranges` (structure.py)

Новый метод, вызывается в начале `_prepare_try`: группирует "сырые"
exception-записи по (catch_type, handler_pc), сшивает ВСЕ диапазоны
одной группы в один span (`min(start)`..`max(end)`) - НЕ требуя строгой
смежности (первая попытка требовала `end предыдущего == start
следующего`, но разрыв в 1 инструкцию сломал это - см. выше про
`ireturn`; ослабил до "просто один и тот же (catch_type, handler_pc) -
считаем одним try", что безопасно, потому что одинаковый handler_pc +
catch_type в пределах ОДНОГО метода практически никогда не бывает
совпадением двух НЕсвязанных try-блоков).

## Побочные находки при валидации фикса (тот же класс бага, что HANDOFF_10)

После починки самого try/catch вылезли ДВЕ новые проявления
int-vs-boolean-бага (HANDOFF_10) в этом же методе - типизация не
дотягивалась досюда:

1. `_inline_single_use_crossing_temps` (engine.py) - сворачивает
   `t = X; return t;` в `return X;`, но брал `X` КАК ЕСТЬ, без повторной
   коррекции типа под `ctx.ret_type`. Итог - `return 0;` при объявленном
   `boolean`-методе. Фикс - оборачиваем `_coerce_arg(cur.expr.value,
   ctx.ret_type)` при инлайне.
2. `_refresh_crossing_temp_types` (engine.py) - тип сквозной (crossing)
   переменной брался из ТИПА ПЕРВОГО присваивания (`__stk4 = 1;` дало
   тип `"int"`), без учёта того, что переменная напрямую возвращается
   `return __stk4;` из `boolean`-метода. Итог - `int __stk4; ...
   __stk4 = 1; ... return __stk4;` - несовпадение типов. Фикс - собираем
   "boolean-подсказки" (явное boolean-присваивание ИЛИ использование как
   значения `return` в boolean-методе), если тип получился `"int"`, но
   есть подсказка - переопределяем на `"boolean"`; дальше отдельным
   проходом конвертируем оставшиеся 0/1-int-константы в этой переменной
   в настоящие `true`/`false`.

`applyPlayerProfileSkullReflect` теперь ПОЛНОСТЬЮ корректен: один
try/catch с 3 нормальными catch-блоками, `boolean __stk4;` с `true`/
`false` литералами, `return false;`/`return __stk4;` - всё типизировано
верно.

## Существенный побочный эффект: `SQLite.getPlayerData()` вышел из
## ПОЛНОГО байткод-фоллбэка

Этот метод (try-with-resources на `ResultSet`/`PreparedStatement`,
`SQLException`) раньше был ЦЕЛИКОМ байткод-дизассемблером (весь метод не
структурировался), теперь - полностью структурированный Java. Похоже, у
него была ТА ЖЕ болезнь со split exception ranges (общая на try-with-
resources генерируемый код, где похожий разрез диапазонов - обычное
дело).

**НО**: в сгенерированном коде замечена ПОДОЗРИТЕЛЬНАЯ строка:

    } catch (Throwable e2) {
        var7 = e2;
        playerLevel.addSuppressed(var7);
        throw playerLevel;
    }

`var7` объявлен как `PlayerLevel var7;` (из основной ветки метода), но
здесь ему присваивается `e2` (`Throwable`) - явное несовпадение типов,
скорее всего НЕ СКОМПИЛИРУЕТСЯ. Это выглядит как "переиспользование
слота" - JVM использует один и тот же local slot для `PlayerLevel`
результата И ДЛЯ Throwable в suppressed-exception-веточке
try-with-resources (стандартный компилятором сгенерированный паттерн
`addSuppressed`), а наш декомпилятор путает их как ОДНУ переменную.
Это НОВАЯ, ОТДЕЛЬНАЯ проблема (не могла проявиться раньше - метод был
ПОЛНОСТЬЮ байткод-фоллбэком, эта деталь просто не была видна). НЕ
чинил - вне рамок этой сессии, нашёл только при валидации основного
фикса.
