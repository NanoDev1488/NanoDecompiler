# HANDOFF_19: v1.4.2 - экран настроек (наконец) + чистка сильно устаревшей
# документации

Пользователь попросил обновить GUI для v1.4.2 и явно спросил, нет ли
незакрытых задач на GUI. Нашёл: экран настроек запрашивался ещё в
`HANDOFF_7_SESSION_AND_TWR_BUG.md` (Аддендум 15, "НЕ СДЕЛАНО"), с тех пор
так и не был реализован - в `App.tsx` не было ни одного тумблера вообще.
Спросил пользователя, какие тумблеры нужны в первую очередь - ответ "оба
сразу" (проверка легитимности + автопроверка обновлений).

## Реализация

**`resources/engine/main.py`** - новый CLI-флаг `--no-legitimacy-check`:
- `process_jar`/`process_jar_with_stats` получили параметр
  `skip_legitimacy=False`.
- Проверка легитимности (GitHub/Modrinth/SpigotMC/RuSpigot) оборачивается
  в `if skip_legitimacy: stats.legitimacy = None else: ...` - `None` уже
  был ДОКУМЕНТИРОВАННЫМ дефолтным значением этого поля в `verify.py`
  (`"dict или None, если не запускалось"`), так что это не новый case для
  downstream-кода (api.py и т.п.), просто теперь достижимый ещё одним
  путём.
- `main()` парсит `--no-legitimacy-check` из `sys.argv` точно так же, как
  уже парсился `--headless` (оба фильтруются из `positional_rest`).
- Проверено вручную (реальный прогон на `EryBuyer-v1.jar`): с флагом и
  без - оба варианта дают идентичные 308/315, с флагом раздел "Проверка
  легитимности" не печатается вообще.

**`electron/main.ts`** - персистентное хранилище настроек:
- Простой JSON-файл `<userData>/settings.json` (НЕ electron-store - для
  двух булевых полей отдельная зависимость избыточна). `loadSettings()`
  разбирает каждое поле ПО ОТДЕЛЬНОСТИ (не просто `{...DEFAULT,
  ...parsed}`) - если файл содержит мусор по одному конкретному ключу,
  берётся дефолт ИМЕННО для него, а не роняются все настройки разом.
- IPC-хендлеры `settings:get`/`settings:set`.
- `run:decompile` перед спавном движка читает `loadSettings()` и
  добавляет `--no-legitimacy-check` в `scriptArgs`, если тумблер выключен.

**`electron/preload.ts`/`src/global.d.ts`** - `getSettings()`/
`setSettings()` в `window.nano`, типы `AppSettings`.

**`src/App.tsx`** - шестерёнка (⚙) в топбаре, модалка с двумя `<label
className="settings-row">` (чекбокс + подпись + пояснение). Настройки
подгружаются один раз при монтировании (`useEffect` с `[]`). Тумблер
"автопроверка обновлений" завязан на УЖЕ существующий эффект проверки
обновлений (`CHECK_INTERVAL_MS` / `runUpdateCheck`) - эффект теперь ждёт,
пока `settings !== null` (иначе бы мигнул проверкой один раз, пока
настройки ещё грузятся, даже если пользователь его выключил), и не
запускает `setInterval` вовсе, если `!settings.autoUpdateCheck`. Когда
автопроверка выключена и `updateState === "idle"` - показывается кнопка
"Проверить обновления" (иначе пользователь был бы вообще без способа
узнать про новую версию).

**`src/styles.css`** - стили под уже существующий тёмный терминал-стиль
(`--surface-container`, `--outline-strong` и т.д., та же палитра, что и
остальной UI) - `.settings-gear`, `.modal-overlay`, `.modal-panel`,
`.settings-row` и связанные классы.

## Проверка (важная оговорка)

**В песочнице этой сессии нет сети** (`npm install` вернул `403
Forbidden` от registry.npmjs.org) - значит НЕТ `node_modules`, а без них
НЕТ реального `tsc`-тайпчека и НЕТ возможности собрать/открыть клиент на
экране. Проверено ТОЛЬКО:
- Баланс `{}`/`()` во всех 4 изменённых TS/TSX-файлах (вручную через
  `content.count()` - грубая эвристика, но лучше, чем ничего).
- Ручное построчное чтение каждого изменённого файла целиком - типы
  согласованы между `preload.ts`/`global.d.ts`/`App.tsx` (одинаковая
  форма `{legitimacyCheck: boolean; autoUpdateCheck: boolean}` везде).
- Python-часть (флаг `--no-legitimacy-check`) - РЕАЛЬНО прогнана на
  `EryBuyer-v1.jar`, полноценно проверена.

**Перед публикацией v1.4.2 обязательно нужно** (не сделано в этой
сессии, нет возможности в песочнице): `npm install` (сеть),
`npm run build` (проверит tsc реально), `npm start` и открыть настройки
глазами хотя бы раз - визуально проверить модалку/тумблеры, что клик по
шестерёнке не ломается, что чекбоксы реально сохраняются между
перезапусками.

## Побочная находка и чистка: README сильно устарел

При обзоре GUI-состояния наткнулся на то, что `README.md` всё ещё
ПОЛНОСТЬЮ описывал старый, физически удалённый GUI:

- Раздел "GUI (Windows)" описывал три темы (MD3/Неоновая/Сырая) через
  `gui_md3.py`/`gui_neon.py`/`gui_raw.py`/`gui.py` - ВСЕ четыре файла
  физически удалены из репозитория (см. `HANDOFF_4_ELECTRON_AND_FIXES.md`
  - миграция на Electron), только `gui_common.py` выжил (и то теперь про
  другое - `jar_summary()`/`get_app_data_dir()`, не про темы).
- Раздел "Сборка в .exe" всё ещё учил собирать ОДИН .exe через голый
  PyInstaller с `--hidden-import=customtkinter --collect-all flet` -
  реальность: ДВА раздельных артефакта (`NanoDecompilerCLI.exe` через
  pyinstaller - headless движок, И `NanoDecompiler-Client-Setup.exe`
  через `electron-builder` - GUI-клиент).
- "Диагностика проблем" учила чинить "не переключается тема GUI" - темы
  давно нет вообще.
- "Быстрый старт" (Windows) говорил, что `run.bat` "откроется GUI" -
  теперь `run.bat` без аргументов просто печатает usage (см. main.py -
  ветка "Windows без аргументов" уже была переделана РАНЬШЕ, до этой
  сессии, чтобы не пытаться открыть несуществующий GUI - но текст
  комментария в САМОМ `run.bat` и в README этого не отражал).
- Битый якорь в оглавлении (`#gui-windows` вместо актуального
  `#gui-windowsmacoslinux` после переименования заголовка).

Всё переписано под реальную архитектуру. `run.bat`'s собственный
комментарий тоже поправлен (тот же самый устаревший "откроется GUI").
