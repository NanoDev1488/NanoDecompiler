# HANDOFF_49: ObjectMethods.bootstrap (record'ы) + фикс двойных скобок у Cast

Продолжение HANDOFF_48. Запрос пользователя: "улучшай читаемость декомпилятора,
100% декомпиляции - в конце".

## АНАЛИЗ: КУДА ВКЛАДЫВАТЬСЯ

Собрал `fallback_reasons` со всего тестового корпуса (13 базовых + malware +
BukkitOfUtils), агрегировал по типу причины:

```
143  нередуцируемый goto
111  после структуризации остались недостижимые из AST, но живые по CFG блоки
 54  неподдерживаемый invokedynamic bootstrap: java/lang/runtime/ObjectMethods.bootstrap
 40  switch(String) через hashCode - структуризация ненадёжна
 18  двойное пересечение стека не поддерживается
 12  unrecognized <init> pattern
  ...
```

Топ-2 (goto/недостижимые блоки, вместе больше половины) - это нередуцируемый
control flow, требует серьёзной алгоритмической работы (node splitting или
аналог) - риск внести баги, если делать наспех. Отложил на отдельную сессию.

Взял #3 - **`ObjectMethods.bootstrap`** (54 вхождения) - т.к. это, в отличие
от нередуцируемого control flow, СТРОГО специфицированный (JEP 384/395,
JDK 16+) механизм, а не что-то требующее эвристик.

## ЧТО СДЕЛАНО

`ObjectMethods.bootstrap` генерирует `equals()`/`hashCode()`/`toString()`
для `record`-классов. Формат bootstrap-аргументов специфицирован: Class
самого record'а, String со списком имён компонентов через `;`, дальше -
MethodHandle-геттеры каждого компонента, в том же порядке.

Реализовано в `stackvm.cpp::build_object_methods()`, подключено в
`handle_invokedynamic()`. **Сознательное решение**: генерирую ЧИТАЕМЫЙ
идиоматичный код (`Objects.hash(...)`, `Objects.equals(...)`, конкатенация
в toString), а не пытаюсь побитово воспроизвести внутренний алгоритм
JDK - hashCode() у record'ов НЕ специфицирован точным значением ни в JLS,
ни в JEP, так что это не нужно и невозможно в общем случае; главное -
итоговый equals()/hashCode() соблюдает контракт. Известное упрощение: для
полей-массивов используется `Objects.equals` (ссылочное сравнение), а не
`Arrays.equals` (глубокое) - редкий случай на практике для record'ов.

**Побочный фикс**: `Cast` в AST заявлял приоритет 85, хотя сам ВСЕГДА
самообёртывается в скобки при печати (`"((Type) expr)"`) - из-за этого
вызывающий код (`FieldAccess`/`BinOp` и т.д.) добавлял ЕЩЁ одну пару
скобок поверх уже готового результата: `(((Type) expr))`. Особенно
заметно стало на сгенерированном equals() (много кастов подряд). Поднял
`Cast::prec()` до 100 (эффективно "уже готовое выражение, не трогать") и
завёл отдельную `paren_at(expr, threshold)` в `emit.cpp` для ВНУТРЕННЕЙ
проверки "нужны ли скобки операнду каста" (сохранил историческое значение
85 именно там, чтобы не создать обратную проблему - недостающие скобки
для operand'а). Это касается ВСЕХ каст-выражений в выводе, не только
record equals().

## ПРОВЕРКА

Полная регрессия (13 базовых + malware-образец + BukkitOfUtils) - 0
падений, 0 протёкших маркеров. Реальный прирост:
- `ChatFilterPlus_v2_3`: 91.5% -> 94.9%
- `TowerClans-2_5_2`: 93.6% -> 95.5%
- `WorldGuard-Translator-1_1_1`: 91.3% -> 95.7%
- `BukkitOfUtils-1_19_0`: (после фильтра библиотек из HANDOFF_48) 97.0%

Вручную проверил вывод (`LinksManager_LinkMatch.java`, record с 3 полями) -
корректный `equals`/`hashCode`/`toString`, без двойных скобок,
компилируемый (визуально) код.

## ЧТО ДАЛЬШЕ (для 100%, по приоритету)

1. `switch(String)` через hashCode (40 вхождений) - уже частично
   поддержан, ненадёжен в части случаев - следующая цель, тоже
   специфицированный паттерн (javac всегда компилирует одинаково), должно
   быть тоже tractable.
2. Нередуцируемый goto / недостижимые-но-живые блоки (143+111=254,
   больше половины всех оставшихсяfallback) - самая большая, но и самая
   рискованная категория, нужна отдельная сессия с осторожным подходом.
3. Рендеринг `record`-классов как `record Name(...) { }` вместо `class
   Name extends Record { поля + explicit constructor + accessors }` -
   косметика поверх уже работающей логики (класс и так корректно
   компилируется), не влияет на % декомпиляции, чисто readability.
4. `unrecognized <init> pattern` (12), "двойное пересечение стека" (18) -
   более мелкие категории.
