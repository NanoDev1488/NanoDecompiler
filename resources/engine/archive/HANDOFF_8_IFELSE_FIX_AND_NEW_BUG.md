# HANDOFF_8: If/else-баг (HANDOFF_7 Аддендум 13) - ПОЧИНЕН, проверено на
# реальном EryBuyer-v1.jar. Плюс отдельный, ранее НЕ описанный баг найден
# (не мой регресс - существовал ДО этой сессии).

Пользователь прислал `test_jars/EryBuyer-v1.jar` - впервые в этой ветке
сессий появилась возможность прогнать РЕАЛЬНУЮ регрессию (раньше песочница
была без единого test_jar и без сети).

## Фикс: `structure.py::_build_if_inner` / новый `_find_forward_merge`

Корень бага - см. HANDOFF_7 Аддендум 13, там уже подробно описан. Кратко:
когда `ipdom(pc)` для if/else не находится (типично - консервативные рёбра
исключений мешают), а ОБЕ ветки терминируют (return/throw) РАЗНЫМИ путями -
`merge` оставался `None`, и вызывающий `region()` считал, что поток
прервался, обрывая построение сразу после первого `if` вместо того, чтобы
узнать реальную точку схождения (обычно она физически существует - просто
скрыта от `ipdom` теми же консервативными рёбрами).

Добавлен `_find_forward_merge(true_t, false_t, stop_addrs)` - когда XOR-
случай (`t_term and not f_term` / `f_term and not t_term`) не сработал,
ищет реальную точку схождения напрямую по CFG: ограниченный BFS вперёд от
обеих веток, пересечение достижимых множеств, берёт наименьший адрес.

ДВЕ ловушки, обе пойманы и исправлены В ЭТОЙ ЖЕ сессии, не оставлены на
потом:

1. **Первая попытка проваливалась внутрь catch-блоков** - `cfg.py`
   подмешивает рёбра `try -> handler` прямо в `block.succs` (без пометки
   "это рёбра исключений"), поэтому голый BFS находил "общую точку" внутри
   обработчика исключений - в итоге в код текла мусорная `__caught__`-
   переменная и мёртвый `return` после уже нужного кода. Исправлено:
   BFS не заходит в блоки с непустым `handler_types` (это и есть признак
   "вход в обработчик").
2. **Вторая попытка (уже без catch-проблемы) сломала РЕАЛЬНЫЙ работавший
   метод** - `SkullUtils.invokeSetSkin` (while-цикл с `continue`) ушёл в
   байткод-фоллбэк, которого раньше не было. Причина: BFS шёл по ВСЕМ
   рёбрам вперёд, включая back-edge цикла (`continue` -> начало цикла) -
   внутри цикла почти всё технически достижимо из всего, и
   `min(общие_блоки)` переставал что-либо значить. Исправлено: BFS идёт
   ТОЛЬКО по рёбрам с `target > текущий_pc` (компилятор раскладывает код
   линейно вперёд - обратные рёбра это всегда циклы, не нужны для поиска
   merge).

После обоих исправлений - **чистый выигрыш, НИ ОДНОГО регресса**:

```
EryBuyer-v1.jar: 289/315 (91.7%) -> 293/315 (93.0%)
Фоллбэков: 26 -> 22
```

Причины отката: "переменная объявлена в блоке, но используется за его
пределами" (switch(String) hashCode-паттерн) - была 2, стала 0 (оба
метода почищены). "нередуцируемый goto" - была 5, стала 3. "нередуцируемый
переход внутри региона" - БЕЗ ИЗМЕНЕНИЙ (11 и там, и там) - то есть
никакой метод не сломался в эту категорию, только чинились существующие
фоллбэки.

**Конкретные подтверждённые улучшения** (полный список из diff всех .java,
6 файлов изменилось):
- `InventoryListener.onInventoryClick()` - раньше ПОЛНОСТЬЮ байткод-
  фоллбэк (196 строк дизассемблера), теперь чистый структурированный
  Java с вложенными if/else (клики по GUI, автобай, ClickType-логика).
- `MaterialHeadParser.parse()` - то же самое, раньше фоллбэк, теперь
  корректный вложенный if/else (basehead-/texture- парсинг).
- `SkullUtils.invokeSetTextures()` и ещё один reflection-метод
  (`applyPlayerProfileSkullReflect`-соседний, метод поиска
  `createPlayerProfile` через reflection) - оба раньше фоллбэк, теперь
  структурированный код (while+reflection-цикл).
- `Metrics_MetricsBase`/`Metrics_SimplePie`/`ItemStackService` - были УЖЕ
  "успешны" и раньше, но с дублирующимся/избыточным кодом (напр. один и
  тот же byte[] заполнялся ДВАЖДЫ разными путями) - теперь чище,
  семантически эквивалентно, без дублирования.

## ЧТО НЕ ПОЧИНЕНО этим фиксом (важно не путать)

**Исходный репро-кейс из HANDOFF_7 Аддендум 13 - `SQLite.isConnected()` -
ОСТАЛСЯ БЕЗ ИЗМЕНЕНИЙ**, всё ещё содержит баг (`if (connection == null) {
__stk1 = 0; } __stk1 = !connection.isClosed();` - выполнится ДАЖЕ при
`connection == null`, потенциальный NPE). Прямое сравнение файлов
подтверждает - `SQLite.java` НЕ попал в список изменившихся после фикса.
Значит для ЭТОГО конкретного метода `merge` находится каким-то другим
путём (не через `_find_forward_merge` - видимо, XOR-ветка срабатывает
здесь иначе, или блок 24 недостижим по чисто forward-рёбрам от одной из
веток из-за особенностей конкретно ЭТОГО try/catch). НЕ РАЗБИРАЛСЯ
дальше почему именно этот метод не подхватился - следующей сессии стоит
приоритетно посмотреть именно на него, раз это был исходный репро.

## НОВЫЙ, ОТДЕЛЬНЫЙ баг найден (НЕ мой регресс - подтверждено, был ДО
## этой сессии, просто раньше не описан)

`SkullUtils.applyPlayerProfileSkullReflect()` - двойной try/catch с
одинаковыми типами исключений (`ClassNotFoundException`/
`MalformedURLException`/`ReflectiveOperationException`) на двух уровнях
вложенности. Сгенерированный код:
- Во ВНЕШНИХ catch-блоках ссылается на `e1`/`e2`/`e3` - переменные,
  объявленные во ВНУТРЕННИХ catch-блоках (другая область видимости) -
  `NameError`-класса баг, гарантированно НЕ компилируется.
- `__stk3`/`__stk4` используются в `return __stk3;`/`return __stk4;`, не
  будучи гарантированно проинициализированными на всех путях (похоже на
  тот же класс проблемы, что и `isConnected()` - расходящиеся пути
  завершения, но здесь ещё сложнее из-за вложенных try/catch).

Подтверждено сравнением с байткодом БАЙТКОДА через `git diff`-подобное
сравнение: этот код был ИДЕНТИЧЕН в baseline (до фикса этой сессии) и
после - фикс `_find_forward_merge` тут вообще не участвовал (метод не
попал в список изменившихся файлов дважды - то есть даже с фиксом
результат для этого метода не поменялся, значит и без фикса баг был
такой же). Это отдельная, ранее не описанная проблема - скорее всего в
том, как строится вложенный try/catch с повторяющимися типами исключений
(`_build_try` в structure.py, где-то в логике генерации имени catch-
переменной/переиспользования имени между уровнями вложенности). НЕ
чинил - вне рамок этой сессии (найден случайно при валидации основного
фикса), не разбирал корень.
