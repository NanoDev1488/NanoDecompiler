## Диагностика (через реальный байткод, не гадание)

Вытащил байткод+exception-table `SQLite.getPlayerData()` напрямую из
.class (`classfile.ClassFile` + `ir.decode_method`). Ключевое: JVM
переиспользует local slot'ы между СОВЕРШЕННО РАЗНЫМИ типами в
компилятором сгенерированном коде try-with-resources с
suppressed-exception (`addSuppressed`):

- slot 6: `PlayerLevel playerLevel` (обычный путь, конструирование
  результата) - ПЕРЕИСПОЛЬЗУЕТСЯ как `Throwable` (перехваченное
  исключение) в обработчике pc=166 (внешний catch(Throwable) вокруг
  `ResultSet.next()`+конструирования).
- slot 7: `PlayerLevel var7` (compiler-generated переменная -
  "финальное значение try-блока") - ПЕРЕИСПОЛЬЗУЕТСЯ как `Throwable` в
  обработчике pc=183 (ВНУТРЕННИЙ catch(Throwable), вложенный в catch
  выше - классический suppressed-exception паттерн: "если close()
  внутри catch тоже бросил - добавить как suppressed к основному").

Это ЛЕГАЛЬНО и типично для JVM (verifier проверяет типобезопасность per
non-overlapping live range, не "один slot = одна Java-переменная на весь
метод"). Движок же (`ctx.locals` в stackvm.py, общий на весь метод) как
раз считает "один slot = одна переменная", поэтому переиспользование
слота 7 даёт `var7 = e2;` при объявленном `PlayerLevel var7;` -
несовпадение типов, НЕ КОМПИЛИРУЕТСЯ.

Механизм для slot 6 УЖЕ существует и (иногда) работает: в `_build_try`
(structure.py) есть проверка - если первый statement тела catch-а
оказывается `LocalDecl` с инициализатором-сентинелом перехваченного
исключения (`CAUGHT_SENTINEL`/`__caught__`), берём ИМЯ из этого decl как
имя catch-переменной (вместо `e1`/`e2`/...) и убираем decl (он избыточен
- параметр catch и так это имя). Это то, что даёт `Throwable playerLevel
= e2;`-подобные строки в других местах.

## Первая попытка фикса - и почему откатил

Добавил ветку: если cbody[0] - это НЕ `LocalDecl`, а простое присваивание
уже объявленной СНАРУЖИ переменной (типичный случай для
crossing-temp'ов вроде `var7`, которые декларируются на уровне метода
ДО того, как любой блок их "увидит", поэтому при перехвате исключения в
этот же slot получается plain `Assign`, а не свежий `LocalDecl`) -
заводил свежее catch-имя и переименовывал ВСЕ обращения к старому имени
внутри ЭТОГО catch-тела.

Починил компиляционную ошибку (`return false` теперь честно так и
осталось, `var7 = e2` пропал), НО получил ХУЖЕ на выходе:

    } catch (Throwable e2) {
        try {
            result.close();
        } catch (Throwable e2) {
            e2.addSuppressed(e2);   // <- БЫЛО: playerLevel.addSuppressed(var7)
            throw e2;               // <- БЫЛО: throw playerLevel
        }
    }

`e2.addSuppressed(e2)` - самоссылка. Компилируется (синтаксически
валидно - Java разрешает вложенным `catch`-параметрам иметь одинаковое
имя, внутренний `e2` просто затеняет внешний), НО СЕМАНТИЧЕСКИ НЕВЕРНО:
внутренний catch должен добавить СВОЁ (только что пойманное при
`close()`) исключение как suppressed к ВНЕШНЕМУ (основному) исключению
и перебросить ВНЕШНЕЕ - а получилось, что оба имени схлопнулись в одно,
и внутренний `e2` (по правилам области видимости Java) везде внутри
своего блока экранирует внешний. Это ТИШЕ компиляционной ошибки (код
скомпилируется), но хуже по последствиям - результат работает
НЕПРАВИЛЬНО без всякого предупреждения.

**Откачено.** Подтверждено побайтово - после отката вывод идентичен
состоянию до этой попытки (`diff -rq` пустой).

Не смог сходу разобраться, ПОЧЕМУ у outer catch (slot 6) в некоторых
случаях получается чистый `LocalDecl`+извлечение имени (правильный
путь), а в некоторых - остаётся plain `Assign` с оригинальным именем
"playerLevel" в СВОЁМ catch-теле, но САМ catch-параметр всё равно рендерится
как "e2" (не "playerLevel") - похоже, порядок обработки блоков (какой
именно кусок метода стал "первым" для `ctx.locals[slot]`) влияет на то,
попадёт ли catch-тело в ветку "уже объявлено" или "первое объявление
здесь", и это ПЕРЕСЕКАЕТСЯ с проблемой crossing-temp'ов сложным образом,
который я не распутал до конца за отведённое время.

## Рекомендация для будущей сессии (НЕ патч поверх текущей логики)

Патчить точечно `_build_try`/`_refresh_crossing_temp_types` дальше -
рискованно: слишком легко починить один конкретный кейс и тихо сломать
другой (ровно как здесь). Правильный путь, которым идут настоящие
Java-декомпиляторы (CFR, Vineflower) - РАСПОЗНАВАТЬ канонический
байткод-паттерн try-with-resources (включая двойной nested try/catch с
`addSuppressed`) ЦЕЛИКОМ как единую структуру и пересобирать её в
сахарную форму `try (Resource r = ...) { ... }` - тогда compiler-
generated временные переменные (playerLevel-как-Throwable, var7-как-
Throwable) вообще не нужно именовать по отдельности - их просто нет в
пересобранном виде. Это отдельный, некороткий таск (нужен
pattern-matcher на форму exception-table + CFG-shape для try-with-
resources), не однострочный фикс.

Альтернатива поменьше - научить `ctx.locals` понимать НЕСКОЛЬКО
"поколений" для одного slot (расщепление по live-range, а не по всему
методу разом - классическая техника "variable splitting"/SSA-подобный
подход) - тоже нетривиально и требует анализа live-range пересечений
per-slot по всему CFG, не только внутри одного `_build_try`.
