## Выбор языка: C++17

Из вариантов C/C++/C#/C-- (см. HANDOFF_23 п. "общий порядок работ"):
выбран **C++17**. Причины:
- Не C: constant pool JVM - это по сути tagged union/variant с ~15
  разными формами записи (Utf8/Class/Fieldref/...); в чистом C это
  либо огромный switch на void* с ручным управлением памятью, либо
  боль. В C++ - `std::variant`-подобная структура, `std::optional`,
  RAII - тот же уровень контроля, что и C, без ручных malloc/free на
  каждый чих.
- Не C#/C--: не входят в стандартный набор toolchain'ов, доступных в
  этом контейнере без сети (нет доступа в интернет для установки
  .NET SDK и т.п. - см. ниже "окружение"); C++ компилятор (g++ 13.3)
  уже есть.
- Дерево зависимостей внутри Python-движка (classfile -> javatypes/
  opcodes -> disassembler -> ir -> cfg -> stackvm -> ast_nodes ->
  structure -> emit -> main) переносится в C++ практически 1:1 как
  набор `.hpp`/`.cpp` файлов + структуры/классы - без необходимости
  в рефлексии или динамической типизации, которых Python предоставляет
  "бесплатно", а C++ - нет, но которые в этом коде не особо и
  используются (это не universal object model, это конкретный парсер
  конкретного бинарного формата).

## Структура

Новая директория `resources/engine_cpp/` рядом с `resources/engine/`

## Модуль 1: classfile.py -> classfile.hpp/cpp

Перенесено ПОЛНОСТЬЮ (не подмножество):
- `Reader` (u1/u2/u4/s1/s2/s4/bytes/skip) - побайтовый ридер.
- Constant pool: все 17 тегов, включая Long/Double, занимающие 2
  слота индекса (легко забываемая деталь спеки JVM - специально
  проверено регрессией, см. ниже).
- `Field`/`Method`/`ExceptionEntry`/`LocalVarEntry`/`InnerClassEntry`/
  `BootstrapMethod`.
- Аннотации: `element_value` (JVM spec 4.7.16.1) - все теги
  (примитивы/строка/enum-константа/класс/вложенная аннотация/массив),
  `RuntimeVisible/InvisibleAnnotations`,
  `RuntimeVisible/InvisibleParameterAnnotations` (включая склейку
  Visible+Invisible по параметрам, как в оригинале).
- Атрибуты: `ConstantValue`, `Signature` (класс/поле/метод),
  `SourceFile`, `BootstrapMethods`, `InnerClasses`, `Code`
  (max_stack/max_locals/raw bytecode/exception table/
  LocalVariableTable - LineNumberTable/StackMapTable/
  LocalVariableTypeTable по-прежнему пропускаются, как и в Python).
- `class_name`/`name_and_type`/`ref_string`/`describe_cp`/`utf8`/
  `access_str` - все resolution-хелперы.

### Найденный и исправленный баг ПОРТА (не в оригинале)

Во время написания оставил "заглушку"-цикл перед реальным циклом
парсинга полей, которая по ошибке дёргала `r.u2()` (то есть реально
читала байты из потока, а не просто заглушка без побочных эффектов) -
это сдвинуло бы позицию ридера и сломало весь дальнейший парсинг.
Поймано ДО прогона регрессии, при повторном чтении собственного кода
- убрано полностью, оставлена одна корректная реализация цикла. Урок
на будущее для этой C++ ветки: `Reader::u2()` в C++ (в отличие от
геттера в Python) - это МЕТОД С ПОБОЧНЫМ ЭФФЕКТОМ (двигает позицию),
и порядок вычисления операндов в одном C++-выражении (например,
`f(r.u2(), r.u2())`) НЕ гарантирован стандартом - в отличие от Python,
где аргументы вычисляются строго слева направо. Поэтому во всём порте
множественные последовательные чтения ВСЕГДА разносятся на отдельные
строки/локальные переменные, а не сворачиваются в одно выражение.
Стоит держать это в голове для всех следующих модулей (особенно
`stackvm.py`/`engine.py`, где таких последовательных чтений/операций
с побочными эффектами будет ещё больше).

### Регрессия / сверка паритета

Инфраструктура: `dump_classfile` (C++) и `dump_classfile_ref.py`
(Python, через оригинальный `classfile.py`) печатают ОДИНАКОВЫЙ по
формату текстовый дамп (класс/супер/access/interfaces/поля/методы/
код-метаданные/локальные переменные/аннотации/inner classes) для
одного `.class` файла - построчный `diff` между ними ловит ЛЮБОЕ
расхождение семантики.

Прогнано на **4075 реальных `.class` файлах**, извлечённых из ВСЕХ 13
тестовых jar (`all-test-jars.zip` - включая оба больших: EryBuyer 13
МБ / 3195 классов и Salaires 20 МБ, а не только маленькие):

```
ChatFilterPlus/DeluxeMenuConstructor/FunnyClans/HeadDatabase/MSG/
NanoQuests/NanoRTP/NanoSpec/TowerClans/WorldGuard-Translator/
rccooldown  -> 880 классов
EryBuyer + Salaires (по отдельности)                -> 3195 классов
```

Результат: **0 расхождений, 0 ошибок парсинга** на всех 4075 классах
(включая один найденный и исправленный по пути баг самого дамп-тула -
разница в форматировании пробела при пустом списке interfaces, не
баг парсера - см. коммит-эквивалент в `tools/dump_classfile.cpp`).

Команды для повтора (пример):
```bash
g++ -std=c++17 -O2 -Wall -Iinclude src/classfile.cpp tools/dump_classfile.cpp -o dump_classfile
python3 tools/dump_classfile_ref.py some.class > py.txt
./dump_classfile some.class > cpp.txt
diff py.txt cpp.txt
```

### Осознанные упрощения (не влияют на паритет данных, только на текст ошибок)

- `describe_cp` в C++ использует упрощённый `'...'`-обёртку вместо
  точного Python `repr()` (escaping спецсимволов). `describe_cp`
  используется только в текстовых комментариях к байткоду (для
  человека), не во flow декомпиляции - при переносе `disassembler.py`
  (следующие модули) нужно решить, важна ли точность до символа, или
  достаточно текущего приближения. Отмечено, не забыть.
- `Utf8` в constant pool: Python декодирует `errors="replace"` (битые
  байты -> U+FFFD), C++ сейчас копирует байты как есть без валидации/
  замены. На всех 4075 реальных классах расхождений не было (валидный
  UTF-8 везде), но это не доказательство на будущее - если попадётся
  jar с битой Modified UTF-8 в constant pool, здесь может обнаружиться
  расхождение. Отмечено как потенциальный TODO, не фиксил вслепую
  (не на чем было проверить конкретное поведение на реальных данных).
