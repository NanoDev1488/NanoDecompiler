# HANDOFF_20: "переменная объявлена в блоке" - разобран до конца, НЕ чинить
# точечно (симптом более глубокой проблемы)

Продолжение исследования, начатого в HANDOFF_17 (раздел 5). Repro:
`ChatFilterPlus.LinksManager.looksLikeLinkCandidate()`.

## Диагностика (обошёл safety-check временно, посмотрел на реальный
## сгенерированный код)

```java
private boolean looksLikeLinkCandidate(String message, LinksManager_LinkSettings arg1) {
    int var3 = message.length();
    int triggers = 0;
    while (true) {
        if (triggers >= var3) {
            triggers = arg1.quickTriggers;      // <- triggers: int -> некий Iterable!
            if (triggers == null) {
                ...
                return true;
            } else {
                Iterator var5 = triggers.iterator();   // var5 объявлена ТОЛЬКО здесь
            }
            while (true) {
                if (!var5.hasNext()) { ... return true; }   // используется СНАРУЖИ if/else
                ...
            }
            return true;
        } else {
            ...
        }
    }
}
```

Раскопал через docstring `_has_escaping_local_decl` (уже была честная
запись: "-8..-14 п.п. успешности на реальных jar" от ПРОШЛОЙ попытки
ослабить именно эту проверку, до этой сессии) - значит точка УЖЕ отмечена
как высокорисковая, дополнительное подтверждение не помешало.

`var5` (переменная, которую формально ловит abort) - лишь СИМПТОМ. Настоящая
проблема глубже: `triggers` меняет ТИП посреди метода (`int` -> некий
`Iterable`-подобный тип) - JVM-слот честно переиспользован под ДВЕ разные
логические переменные (тот же класс проблемы, что и var7 в HANDOFF_12, но
для ОБЫЧНОЙ локальной переменной, не catch-параметра). Плюс сам
`while(true){ if(...) {...} else {...} }` выглядит как слияние ДВУХ
изначально независимых циклов компилятором в одну структуру, которую
движок не смог корректно разъединить.

## Решение: НЕ чинить точечно

`_has_escaping_local_decl` - ЕДИНСТВЕННАЯ причина, почему этот метод не
выдаёт битый Java (типа `int triggers; ... triggers = someIterable;` -
несовпадение типов, либо `var5` вне области видимости - тоже не
компилируется). Ослабление ЭТОЙ конкретной проверки уже один раз стоило
8-14 процентных пунктов на реальных jar (задокументировано в её
собственном docstring) - трогать без готового решения именно КОРНЕВОЙ
проблемы (распознавание слияния циклов / расщепление слота на разные
логические переменные) не стал.

Добавил краткую заметку прямо в docstring `_has_escaping_local_decl` (см.
`engine.py`), чтобы следующая попытка не начинала с нуля и не пыталась
чинить симптом вместо причины.

## Попутно: попытка расширить узкую goto-эвристику на циклы - тоже
## откачена

HANDOFF_18 предлагал постепенно расширять условие "if сразу после
try/catch" (см. `_last_try_merge_pc`) на "if сразу после цикла" тоже.
Попробовал - `_build_loop` тоже начал выставлять этот флаг своим
`exit_pc`. Полный прогон всех 12 jar - ChatFilterPlus просел на 1 метод
(955->954), остальные без изменений. Даже единичная регрессия -
откачено немедленно (см. `diff -rq`, подтверждён чистый откат). Цикл и
try/catch, оказывается, недостаточно похожи для одной и той же
эвристики "право предпочесть более близкую точку схождения" - нужен
отдельный анализ, ПОЧЕМУ здесь один случай регрессировал, прежде чем
пробовать снова.

## Что дальше

Настоящий фикс для этого класса проблем потребует: (а) распознавание
слияния двух циклов компилятором в одну структуру (сложный анализ CFG),
или (б) расщепление одного JVM-слота на несколько логических переменных
по live-range (тот же подход, что нужен для var7 в HANDOFF_12 - см. там
предложение про "variable splitting"/SSA-подобную технику). Оба варианта
- не быстрый фикс, отдельная спроектированная заранее задача.
