# HANDOFF_50: рендеринг record-классов как `record Name(...) { }`

Продолжение HANDOFF_49 (п.3 из списка "что дальше").

## ЧТО СДЕЛАНО

1. `classfile.hpp/.cpp` - добавлен парсинг атрибута `Record` (JVM spec
   4.7.30, JDK 16+) - `ClassFile::record_components` (имя+дескриптор
   каждого компонента, в порядке объявления).
2. `render_class.cpp`:
   - Заголовок класса: `record Name(Type comp1, Type comp2, ...)` вместо
     `class Name extends Record`.
   - Поля-компоненты НЕ печатаются повторно как обычные поля.
   - Тривиальные accessor-методы (`Type comp() { return this.comp; }`) -
     пропускаются, если байткод ТОЧНО совпадает с ожидаемым (5 байт:
     `aload_0; getfield comp; <return>`). При кастомном override -
     печатается как обычно.
   - `equals`/`hashCode`/`toString`, если делегируют В
     `ObjectMethods.bootstrap` НЕИЗМЕНЁННЫМИ (см. HANDOFF_49) -
     пропускаются. При явном override - печатаются как обычно.
   - Канонический конструктор ВСЕГДА печатается явно (сознательный
     компромисс - JLS требует совпадения имён параметров с компонентами,
     а наши параметры берутся из декомпилированного тела; синхронно
     переименовать и сигнатуру, и уже отрендеренный текст тела - отдельная
     более рискованная задача, оставлена на будущее).

Обнаружение "тривиальности" - по ТОЧНОМУ байткоду, не эвристика - при
ложноотрицательном срабатывании последствие - явный, но валидный код,
никогда не пропуск логики или ошибка компиляции.

## ПРОВЕРКА

`LinksManager_LinkMatch` (3 компонента): было `class ... extends Record`
с явными accessor/equals/hashCode/toString (~30 строк), стало
`record LinksManager_LinkMatch(int start, int end, String text) { <ctor> }`
(8 строк). Полная регрессия (13 базовых + malware + BukkitOfUtils) - 0
падений, 0 протёкших маркеров.

## ЧТО ДАЛЬШЕ

1. Синхронное переименование параметров канонического конструктора под
   имена компонентов.
2. `switch(String)`/нередуцируемый goto - см. HANDOFF_49, отдельная сессия.
