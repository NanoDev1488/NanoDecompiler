### Баг в модуле 4 (ir.cpp), пойманный ЭТИМ модулем - см. обновлённый HANDOFF_27

При работе над cfg.cpp обнаружилось, что порт `ir.py` хранил switch-targets
в отсортированной `std::map`, а не в порядке вставки, как Python dict -
`cfg.py` напрямую зависит от этого порядка при построении `succs`.
Исправлено в `ir.hpp`/`ir.cpp` (не в cfg), модуль 4 пересверен заново -
подробности в обновлённом `HANDOFF_27_CPP_PORT_MODULE4_IR.md`. Это
типовой риск межмодульного переноса: баг в уже "сданном" модуле может
не проявиться, пока следующий модуль не начнёт использовать то самое
поведение, которое предыдущий тест не проверял по-настоящему (а только
казался, что проверяет).

### Особенности ОРИГИНАЛА, воспроизведённые намеренно (не баги порта)

1. **`_build`, вычисление `end` последнего блока.** Python:
   `end = leaders[i+1] if ... else (self.order[-1] and
   self.instrs[self.order[-1]].next_pc)`. Из-за трюка `X and Y` в Python
   (возвращает `X`, если `X` ложно) это выражение даёт `0` вместо
   ожидаемого `next_pc`, если `self.order[-1] == 0` - то есть если метод
   состоит РОВНО из одной инструкции на `pc=0`. Это реальный, хоть и
   крайне редкий, латентный баг оригинала (для такого метода последний -
   и единственный - блок получит `end=0`, `instrs=[]`, что дальше
   трактуется как "блок без инструкций" и не получает succs). Порт
   воспроизводит это 1:1 (`(last == 0) ? 0 : ...next_pc`), НЕ исправлено
   - таково правило работы над v2.0: сначала полный перенос с
   побитовым паритетом, потом (отдельным треком, по явной команде) -
   обсуждение, какие баги оригинала стоит осознанно исправить в v2.
2. **Дублирующиеся `handler_types`.** Если try-диапазон исключения
   покрывает НЕСКОЛЬКО базовых блоков, для КАЖДОГО покрывающего блока
   `hb.handler_types.append((catch_type, e))` добавляет ЕЩЁ одну (по сути
   дублирующую) запись в список `handler_types` блока-обработчика - то
   есть один и тот же `(catch_type, ExceptionEntry)` может встретиться в
   этом списке несколько раз. Похоже на недосмотр в оригинале (скорее
   всего имелось в виду добавить запись один раз на exception entry, а не
   на каждый покрывающий блок), но воспроизведено точно как есть.
3. **Порядок `natural_loops()`.** `tails`/`body` в оригинале - Python
   `set` (порядок перебора не гарантирован и не воспроизводился нарочно -
   для сверки оба дампера печатают их отсортированными). А вот порядок
   ЭЛЕМЕНТОВ САМОГО списка `result` (т.е. порядок `header`'ов) -
   воспроизведён точно (порядок первого обнаружения заголовка при обходе
   `blocks.items() x succs`), т.к. это `dict`, для которого Python
   гарантирует порядок вставки.
