# ПЕРЕДАЧА СЛЕДУЮЩЕМУ АГЕНТУ - порядок задач

Читать ВСЕ `HANDOFF_*.md` в этой папке по номеру по порядку перед началом
работы - это не опционально, там объяснены причины архитектурных решений,
которые иначе выглядят непонятными или ошибочными. Особенно важны:
`HANDOFF_39` (изначальный бэклог GUI-задач), `HANDOFF_44-46` (движок на
C++, весь Python удалён), `HANDOFF_51/54` (кроссплатформенный CI).

## ТЕКУЩЕЕ СОСТОЯНИЕ ПРОЕКТА (кратко)

- **Движок**: полностью на C++ (`resources/engine_cpp/`), без единого
  Python-файла в проекте. CLI-бинарник `NanoDecompilerCLI` поддерживает
  обычный режим, `--json-output`, `--api-server` (HTTP), `--jar-summary`,
  `--install-tools[-json]`. Собирается через `CMakeLists.txt`
  (кроссплатформенно) или напрямую `g++ -std=c++17 -O2 -Iinclude src/*.cpp
  -lz -o NanoDecompilerCLI`.
- **Декомпиляция**: на тестовом корпусе (13 базовых jar +
  `test_jars/malware_samples/` + `test_jars/large_legit/`) - 88-100%
  методов восстанавливается в структурированный Java (медиана ~93-97%).
  Портированы: switchmap (свёртка switch-on-enum), naming_hints
  (осмысленные имена), ObjectMethods.bootstrap (record-классы),
  рендеринг `record Name(...) {}` вместо `class extends Record`.
- **GUI**: Electron+React+TS. Добавлена мини-IDE (файловый проводник +
  CodeMirror-редактор, HANDOFF_52) и конфиг-driven мини-язык для
  источников проверки легитимности с сравнением хэшей (HANDOFF_53).
  **НИ РАЗУ не собирался живьём** (`npm install`/`vite build`) за всю
  историю проекта - в песочнице сессий порта нет сети на npm-реестр.
- **CI**: `.github/workflows/build-and-release.yml` - явные job'ы
  `build-client-windows/-linux/-macos` + `build-api` (Windows-only,
  отдельный голый движок) + `publish-release` (требует успеха ВСЕХ трёх
  клиентских job'ов, иначе релиз не публикуется). **НИ РАЗУ не запускался
  живьём** - в песочнице сессий порта нет доступа к GitHub Actions вообще.
- **Версия**: 1.6.2 (`package.json`, `version.hpp`).

## ПОРЯДОК ЗАДАЧ (по приоритету, как просил пользователь)

### 0. СРОЧНО - диагностировать реальный CI-прогон

Пользователь сообщил: в реальном релизе видны файлы ТОЛЬКО под Windows.
Разбито на явные job'ы (HANDOFF_54), но БЕЗ доступа к логам причина не
установлена. **Первым делом**: открыть вкладку Actions в репозитории,
найти последний прогон `build-and-release.yml`, посмотреть логи
`build-client-linux`/`build-client-macos` - на каком шаге упало. Частые
кандидаты: `npm install` без `package-lock.json` (см. предупреждение в
самом workflow), electron-builder платформо-специфичная ошибка,
отсутствие `cmake`/компилятора на образе раннера. Исправить по факту
реальной ошибки, не гадая вслепую (в отличие от прошлых сессий, у
агента с доступом к логам есть возможность получить ТОЧНУЮ причину -
пользуйтесь этим, не пишите новых спекулятивных фиксов "на всякий случай").

### 3. Качество декомпиляции - оставшиеся категории

См. HANDOFF_49 полностью (там аналитика по всему тестовому корпусу).
Самая крупная категория (~254 случая, больше половины всех откатов на
байткод) - нередуцируемый `goto`/недостижимые-но-живые блоки после
структуризации. **Рискованная задача** - требует аккуратной работы с
алгоритмом control-flow структуризации, НЕ делать наспех. Также найден,
но не исправлен реальный баг: `collect_shallow_referenced_names()` в
`engine.cpp` не заглядывает в тела `if`/`while`/`for`/`switch` (только
условия) - в редких случаях может тихо давать НЕКОМПИЛИРУЕМЫЙ код вместо
честного отката (см. HANDOFF_49, раздел "реальный баг").

Меньшие категории: `switch(String)` через hashCode (~40 случаев,
расследовано в HANDOFF_49, оказалось смесью причин), "unrecognized
init pattern" (12), "двойное пересечение стека" (18).

Косметика: параметры канонического конструктора record-классов сейчас
не переименовываются под имена компонентов (HANDOFF_50) - конструктор
всегда явный вместо более чистого варианта.
