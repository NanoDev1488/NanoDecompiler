# Мини-язык конфигурации источников проверки легитимности (HANDOFF_53)

Формализация черновой спецификации пользователя из HANDOFF_39/HANDOFF_23.
Черновик был НЕ валидным JSON и не учитывал, что источники
(GitHub/Modrinth/Spiget/Hangar - до 1.9.6 вместо Hangar был RuSpigot, см.
правку ниже) отдают ОТВЕТ в совершенно разных форматах JSON-API - простой
конкатенации `site + query` недостаточно, чтобы понять, КАК разбирать
ответ. Формализация ниже - осознанная адаптация черновика под реальность,
отличия от буквального текста черновика объяснены по каждому пункту.

## Формат: реальный JSON-массив объектов

```json
[
  {
    "label": "GitHub",
    "kind": "github_api",
    "site": "github.com",
    "query": "https://api.github.com/search/repositories?q={plugin_name}+in:name&per_page=5",
    "release_query": "https://api.github.com/repos/{full_name}/releases/latest"
  },
  {
    "label": "Modrinth",
    "kind": "modrinth_api",
    "site": "modrinth.com",
    "query": "https://api.modrinth.com/v2/search?query={plugin_name}&limit=5",
    "release_query": "https://api.modrinth.com/v2/project/{slug}/version"
  },
  {
    "label": "SpigotMC",
    "kind": "spiget_api",
    "site": "spigotmc.org",
    "query": "https://api.spiget.org/v2/search/resources/{plugin_name}?field=name&size=5",
    "release_query": null
  },
  {
    "label": "Hangar",
    "kind": "hangar_api",
    "site": "hangar.papermc.io",
    "query": "https://hangar.papermc.io/api/v1/projects?q={plugin_name}&limit=5&offset=0",
    "release_query": null
  }
]
```

## Правка 1.9.6 - RuSpigot заменён на Hangar

`RuSpigot` (`spigotmc.ru`, `kind: html_search`) убран из источников по
умолчанию. Причина - при верификации источников в сессии 1.9.6 нашлось
прямое предупреждение сообщества (обсуждение на Habr): искать плагины
СТРОГО на `spigotmc.org`, а не на `.ru` и подобных "копиях" (в т.ч.
`rubukkit.org`) - это известный вектор бэкдоров. Живого подтверждения,
что `spigotmc.ru` сейчас вообще работает и что это официальное русское
зеркало, а не сторонняя/фишинговая копия, тоже не нашлось. Инструмент
легитимности не должен сам держать в списке доверенных источников домен,
который сообщество прямо называет небезопасным. `kind: html_search` как
МЕХАНИЗМ парсинга из движка НЕ убран (он всё ещё общий, не привязан
жёстко к spigotmc.ru) - но имейте в виду ограничение из пункта 2 ниже:
он использует ОДИН фиксированный regex, настроенный конкретно под
HTML-структуру старой страницы RuSpigot, а не универсальный HTML-парсер
- добавлять свой `html_search`-источник с ДРУГОЙ структурой страницы
эта версия движка не умеет (данные придут, но окажутся мусором).

`Hangar` (`hangar.papermc.io`) - официальный репозиторий плагинов
PaperMC (Paper/Velocity), `kind: hangar_api` - НОВЫЙ встроенный тип
(добавлен в 1.9.6). Ответ - `{"result": [{"name", "namespace": {"owner",
"slug"}, "stats": {"stars"}, ...}]}`, структура подтверждена веб-поиском
(официальная документация `hangar.papermc.io/api-docs` + реальные
сторонние обёртки API), но НЕ протестирована вживую (нет сети в
песочнице сессии 1.9.6 - см. оговорку в `legitimacy_check.hpp`).
Хэш-сравнение для Hangar не реализовано - в подтверждённой структуре
ответа не нашлось поля с хэшем файла версии.

## Отличия от черновика пользователя (и почему)

1. **`query`/`release_query` - ПОЛНЫЙ URL-шаблон**, а не суффикс,
   приклеиваемый к `site`. В черновике `site: "site.com/"` +
   `query: "?search={plugin_name}"` подразумевали конкатенацию - для
   реальных источников это не работает (у GitHub поисковый API живёт на
   `api.github.com`, а не на `github.com`; у Modrinth и Spiget - похожая
   ситуация). `site` остался как поле - используется ТОЛЬКО для подписи в
   выводе ("не соответствует: сайт1, сайт2"), не участвует в построении URL.
2. **Добавлено поле `kind`** - строго необходимо: без него движок не может
   понять, как разбирать ответ (JSON какой структуры, или HTML-страница).
   Пять встроенных значений (`github_api`/`modrinth_api`/`spiget_api`/
   `html_search`/`hangar_api` - последний добавлен в 1.9.6, см. выше)
   соответствуют уже существующим источникам (`legitimacy_check.cpp`,
   HANDOFF_32 + 1.9.6) - конфиг НЕ добавляет поддержку принципиально
   новых типов API "с нуля" (это отдельная, более крупная задача -
   писать под каждый новый `kind` отдельный парсер JSON/HTML нужно
   руками в C++, конфиг сам по себе универсальный парсер не создаёт).
3. **`{plugin_name}`** - подставляется ОЧИЩЕННОЕ имя (см. ниже), уже
   url-encoded. **`{full_name}`/`{slug}`** в `release_query` -
   подставляются данными КОНКРЕТНОГО кандидата, найденного через `query`
   (полное имя репозитория для GitHub, slug проекта для Modrinth) - НЕ
   плейсхолдер уровня всего запроса, а per-candidate.
4. **Очистка имени плагина** (`clean_plugin_name_for_search()`,
   `legitimacy_check.cpp`): отрезаем хвостовой `v`+цифры или отдельный
   версионный суффикс (`-1.2.3`, `_v2`, голые цифры в конце через
   разделитель). Если очищенное имя короче 2 символов - источник вообще
   не запрашивается для этого плагина (пустой `LegitimacySourceResult`,
   `checked=false`) - как и было указано в черновике.

## Сравнение хэшей (новая фича, не было в HANDOFF_32)

Для КАЖДОГО кандидата, у которого есть способ получить хэш файла без
дорогого скачивания произвольных объёмов (см. ограничения ниже),
вычисляется SHA-256 и сравнивается с SHA-256 самого проверяемого `.jar`.
Итог - `HashComparisonResult` (см. `legitimacy_check.hpp`):
`matching` (список меток источников, где хэш совпал) и `mismatching`
(где не совпал, но кандидат найден и хэш получен).

**Реализовано только для источников, где хэш получить дёшево и
надёжно**:
- **Modrinth** - `release_query` (`/version`) отдаёт готовый
  `files[].hashes.sha256` в JSON - НЕ требует скачивания файла целиком.
- **GitHub** - у `releases/latest` нет готового хэша, но есть прямая
  ссылка на ассет - скачивается САМ ассет (с лимитом 50 МБ и таймаутом,
  см. `download_and_sha256` в коде) и хэшируется.

**НЕ реализовано (кандидаты показываются, но хэш не сравнивается)**:
- **SpigotMC (Spiget API)** - API отдаёт только метаданные (без прямой
  ссылки на файл без доп. авторизации/премиум-ресурсов в общем случае) -
  риск скачать не тот файл или упереться в paywall выше пользы.
- **RuSpigot** (HTML-скрейпинг) - нет структурированного API вообще,
  надёжно найти прямую ссылку на файл на странице - отдельная, более
  хрупкая задача, не делалась в этой сессии.

## Загрузка конфига: GitHub + локальный fallback

`load_legitimacy_sites_config()`:
1. Пытается скачать JSON с `LEGITIMACY_SITES_CONFIG_URL` (константа в
   коде, см. ниже) через `http_get` (тот же curl-механизм, что и весь
   остальной сетевой код движка).
2. При успехе - кэширует локально (`<tools_dir>/legitimacy_sites.json`,
   тот же каталог, что и `toolinstaller.hpp::get_tools_dir()`).
3. При неудаче (нет сети/невалидный JSON) - берёт локальный кэш, если он
   есть от прошлого успешного запроса.
4. Если и кэша нет - использует ВСТРОЕННЫЙ дефолт (см. пример JSON выше,
   зашит в код как `default_legitimacy_sites_config()`) - движок
   ВСЕГДА может проверить легитимность хотя бы по 4 базовым источникам,
   даже без единого успешного сетевого запроса за всю историю установки.

**`LEGITIMACY_SITES_CONFIG_URL` - ЗАГЛУШКА**: строка-константа в коде
указывает на несуществующий пока адрес
(`https://raw.githubusercontent.com/USER/REPO/main/legitimacy_sites.json`) -
у меня нет реального GitHub-репозитория пользователя, куда положить этот
файл. Нужно: (1) завести реальный файл в вашем репозитории проекта (или
любом другом публичном), (2) поменять константу на настоящий raw-URL.
До этого шага сетевая загрузка конфига будет молча проваливаться (curl
получит 404) и движок будет использовать встроенный дефолт - это
БЕЗОПАСНОЕ поведение (деградация, не падение), но саму фичу "менять
источники без пересборки движка" нужно включить руками.

## Честная оговорка

Как и весь остальной сетевой код `legitimacy_check.cpp` (см. предупреждение
в шапке файла, HANDOFF_32) - НЕ протестировано вживую (нет исходящей сети
в песочнице сессии порта). Офлайн-тестируемая часть (очистка имени,
разбор JSON-конфига, построение URL по шаблону) протестирована на
синтетических данных - см. HANDOFF_53.
