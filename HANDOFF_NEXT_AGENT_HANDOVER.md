## Что сделано в этом проходе (v1.7.8 «Точность»)

Пользователь прислал реальные jar'ы: `NanoCore.jar` (свой некластерный
инструмент, без plugin.yml), `NanoCore-bundle.jar` (177 МБ, бандлит внутри
`velocity-patched.jar`/`BungeeCord-patched.jar`/2× `paper-*-nanocore.jar`),
`paper-1_21_4-nanocore.jar` и `paper-1_21_11-nanocore.jar` (Paperclip-
загрузчики), `NanoForge-1_4_0__1_.jar` (реальный компилированный jar,
раньше были только исходники).

1. **HANDOFF_URGENT п.15 ЗАКРЫТ - реальный движковый баг, не выдумка
   пользователя.** `paper-*-nanocore.jar` декомпилировался в 0 java-файлов.
   Причина: `known_libs()` в `pom_builder.cpp` содержала запись с префиксом
   `"io.papermc"` (не `"io.papermc.paper"`) - matчила ЛЮБОЙ подпакет
   `io.papermc.*`, включая `io.papermc.paperclip` (собственный код
   Paperclip-загрузчика, 6 классов, которые НУЖНО было декомпилировать).
   Все 259 классов jar'а уходили в `library_classes_skipped`, 0 из 0
   методов - выглядело как "не декомпилируется вообще". Сузил префикс до
   `"io.papermc.paper"` - подтверждено на реальном jar'е (было 0/0 методов,
   стало 34/43, 79%).

   Вторая часть той же жалобы ("META-INF всё ещё остаётся") - отдельная
   причина: Paperclip бандлит ПОЛНЫЙ Maven-кэш зависимостей ЦЕЛЕВОГО
   сервера под `META-INF/libraries/**/*.jar`(.patch) + бинарные
   bsdiff-патчи под `META-INF/versions/**/*.jar.patch` (энтропия 8.0/8.0) -
   `process_jar.cpp` копировал их как обычные "ресурсы" (тем же путём, что
   уже фильтрует `META-INF/LICENSE*`/`proguard/*`). Добавил такой же
   regex-фильтр для этих двух паттернов - вывод для реального jar'а
   пользователя упал с 52 МБ до 204 КБ. Подтверждено на ОБОИХ
   `paper-1.21.4` и `paper-1.21.11`.

   Полная регрессия (17 jar: 13 общего корпуса + 4 новых) - `diff -rq`
   нулевой на всём остальном корпусе, никаких побочных эффектов.

2. **HANDOFF_URGENT п.2 ЗАКРЫТ** - `PluginDetailsModal.tsx`,
   `library_names_hit.join(", ")` заменён на компонент `LibraryNamesValue`
   (первые 3 + разворачиваемый по клику счётчик остальных). `Row.value`
   расширен с `string` до `ReactNode`.

3. **HANDOFF_URGENT п.16 ЗАКРЫТ** - `engine.tsx`, `classifyLine()`.
   Заголовок блока малварь-находок ловился регэкспом `/вредоносн/i` и
   красился как `err`, но КАЖДАЯ отдельная находка печатается движком
   отдельной строкой вида `  [!!!] <описание> (<где>)` (см.
   `format_findings_for_console()` в `malware_scan.cpp`) - слово
   "вредоносн" в них не повторяется, строки проваливались в default `info`.
   Добавлен отдельный regex `/^\s*\[\s*(!!!|!|·)\s*\]\s/` -> `warn`,
   по просьбе пользователя именно "warning, не error/info" для этих строк.

4. **HANDOFF_URGENT п.10 ПРОВЕРЕН, БАГА НЕТ** - сравнил декомпилированный
   `NanoCommand.java` (из `NanoForge-1_4_0__1_.jar`) с реальным исходником
   1.4.0. Диспетчер команд (`switch(args[0].toLowerCase())`, 15 case)
   декомпилятор восстановил корректно как `switch`. If-цепочки НИЖЕ (по
   `args.length` для tab-complete) - это авторский стиль, В ИСХОДНИКЕ
   так и написано, НЕ `switch(String)`-паттерн вообще - декомпилятор ничего
   не потерял. Закрыто без изменений кода.

5. **HANDOFF_URGENT п.5 ЗАКРЫТ** - `process_jar.cpp`, вызов `build_pom()`.
   Реальный тест - `NanoCore.jar` пользователя (нет `plugin.yml`/любого
   манифеста вообще) генерировал pom.xml БЕЗУСЛОВНО, при этом
   сгенерированный файл ВРАЛ в собственном комментарии ("Источники:
   plugin.yml + эвристика по импортам") - plugin.yml в jar'е не было
   вовсе. Теперь pom.xml пишется только если (а) это найденный ОРИГИНАЛ
   внутри jar (`pom_result.source == "original"` - реальные данные) или
   (б) платформа опознана хоть как-то (`kind != Unknown`). Подтверждено:
   `NanoCore.jar` (Unknown, сгенерированный) - pom.xml больше НЕ пишется;
   `paper-1_21_4-nanocore.jar` (Unknown, но с НАСТОЯЩИМ maven-pom внутри
   Paperclip) - pom.xml пишется, потому что это оригинал, не догадка;
   весь остальной корпус (известные платформы) - pom.xml как раньше, 0
   отличий по `diff -rq`.

5. **HANDOFF_URGENT п.1 ПРОВЕРЕН, БАГА НЕ НАЙДЕНО** (см. предыдущую
   переписку с пользователем) - прошёл всю цепочку
   `run()`/`startedAtRef`/`finalize()`/`startQueue()` в `engine.tsx`,
   `elapsedMs` корректно изолирован по job'у, время ожидания в очереди
   (`setTimeout(400ms)` в `finalize()`) не попадает в измерение следующего
   job'а. Не исключено, что жалоба была на старую сборку (см. раздел ниже
   "пользователь тестирует старые сборки").

6. **Сверка списка файлов 1.4.0 исходник vs декомпилят** - `comm -13/-23`
   между списками `.java`: единственное расхождение - `Metrics.java`
   (bStats, корректно фильтруется как известная библиотека,
   `library_names_hit` подтверждает) и 3 файла inner-class-flattening
   (`MenuManager_PendingActionEdit.java` и т.п. вместо `Foo$Bar.class`) -
   оба случая ожидаемы, не баги.

## Важные правила проекта (повторение, чтобы не забыть)

- **DecompileAbort принцип**: при малейшей неуверенности - честный откат к
  байткоду вместо "красивого", но потенциально неверного decompiled-кода.
- **Единый источник версии**: только `package.json` + `version.hpp`
  (`NANO_DECOMPILER_VERSION` - ОДНА константа, не дублировать).
- **НЕ включать бинарники в архив**, отдаваемый пользователю - только
  исходники. Компилировать локально только для собственной регрессии.
- **НЕ трогать `structure.cpp`** без полной регрессии на РЕАЛЬНЫХ jar.
- **Каждое изменение render_class.cpp/движковой логики декомпиляции -
  ОБЯЗАТЕЛЬНО прогонять полную регрессию на всём корпусе ДО и ПОСЛЕ,
  сравнивая проценты И `diff -rq` выходных файлов.**
- global.d.ts и preload.ts ДОЛЖНЫ быть синхронны при добавлении новых
  `window.nano.*` методов.
- Каждые 5-10 исправленных пунктов - собери архив (без .git, без
  бинарников) и отдай пользователю.
