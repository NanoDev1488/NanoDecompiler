## Главное в этом проходе: полная реконструкция enum-констант

Самый ценный фикс сессии - `render_class.cpp`, функция `render_class()`,
блок вокруг `enum_const_fields`/`enum_ctor_reconstructed`. Раньше
(HANDOFF_42-упрощение) `<clinit>` enum'а ВСЕГДА обходился стороной -
константы печатались голыми именами без аргументов конструктора. Паттерн
`enum X { A(1,"a"); X(int n, String s){...} }` встретился в 32 из 32
тестовых jar с enum'ами - системная, очень частая проблема.

Теперь `<clinit>` декомпилируется ТЕМ ЖЕ путём, что и обычный `static{}`
(`decompile_method_body`), и КАЖДАЯ строка вида `EnumType.CONST = new
EnumType(имя, ordinal, арг1, арг2, ...);` (ровно так javac компилирует
список констант) разбирается: два синтетических первых аргумента (имя,
ordinal) отбрасываются, остальные становятся реальными аргументами
константы в выводе. Заодно восстанавливается ЛЮБАЯ ДОПОЛНИТЕЛЬНАЯ
static-инициализация в `<clinit>` enum'а (например заполнение lookup-
таблицы `Map<String,EnumType>` - раньше терялось молча, подтверждено на
реальном `CasinoType` из корпуса - `getType()` теперь реально работает).

**Правило безопасности** (важно не нарушить при доработке): если ХОТЬ ОДНА
константа не укладывается в ожидаемый паттерн (главный случай - анонимное
тело константы `RED { public String toString(){...} }`, компилируется в
NEW отдельного синтетического подкласса, а не самого EnumType) -
реконструкция откатывается ЦЕЛИКОМ для ВСЕГО enum'а (флаг `ok`/`reconstructed`
сбрасывается в false), никогда не делается частично/вперемешку. Это
проверено на реальных jar - в `betterstructures.jar` (`Scanners.java`,
`Vfs_DefaultUrlTypes.java`) откат сработал корректно на enum'ах с
`implements`-интерфейсами и, судя по всему, анонимными телами.

**Не сделано намеренно**: enum-константы с анонимным телом (`RED { ... }`)
по-прежнему НЕ реконструируются - это отдельная, более сложная задача
(нужно распознавать NEW отдельного синтетического подкласса + связывать
его методы с "телом" константы). `<clinit>` enum'а по-прежнему НЕ считается
в статистике "X из Y методов" ни при успехе, ни при откате - сохранено
специально, чтобы не менять знаменатели процентов у всего корпуса при
этом фиксе (если возьмёшься это исправлять - учти, что ВСЕ проценты в
регрессионных логах текущей сессии станут неприменимы для сравнения).

Debug-приём, который пригодится снова: чтобы понять, какую именно форму
AST выдаёт `decompile_method_body()` для конкретного паттерна байткода
(перед тем как писать код распознавания) - временно вставить
`std::fprintf(stderr, ...)`-дамп типов/полей узлов AST (ExprKind как int,
имена полей и т.д.), собрать debug-бинарник ОТДЕЛЬНО (`-o
/tmp/NanoDecompilerCLI_dbg`, не перезаписывая рабочий бинарник), прогнать
на реальном jar с этим паттерном, посмотреть вывод, и ТОЛЬКО ПОТОМ писать
финальный код распознавания - вместо угадывания структуры AST по хэдерам.

## Важные правила проекта (повторение, чтобы не забыть)

- **DecompileAbort принцип**: при малейшей неуверенности - честный откат к
  байткоду вместо "красивого", но потенциально неверного decompiled-кода.
  Ключевой пример из этой сессии - реконструкция enum-констант: ЛЮБОЕ
  несовпадение формы AST с ожидаемым паттерном -> откат ЦЕЛИКОМ, не частично.
- **C++ order-of-evaluation**: НИКОГДА не полагаться на порядок вычисления
  сайд-эффектных вызовов (`r.u2()` и т.п.) внутри одного выражения.
- **Единый источник версии**: только `package.json` + `version.hpp`.
- **НЕ включать бинарники в архив**, отдаваемый пользователю - только
  исходники. Компилировать локально только для собственной регрессии.
- **НЕ трогать `structure.cpp`** без полной регрессии на РЕАЛЬНЫХ jar.
- Библиотечный фильтр (`known_libs()`/`pom_builder.hpp`) - осторожно с
  ложными срабатываниями.
- **Каждое изменение render_class.cpp/movntic логику декомпиляции -
  ОБЯЗАТЕЛЬНО прогонять полную регрессию на всём тестовом корпусе ДО и
  ПОСЛЕ, сравнивая проценты И diff -rq выходных файлов** - именно так в
  этой сессии были пойманы 0 регрессий при добавлении крупного фикса.
